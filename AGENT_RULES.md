# Правила для агента при написании кода

> Ссылайся на этот файл в промпте: «Пиши код по правилам из AGENT_RULES.md».
> Основано на реальных багах, найденных в этом репозитории — каждое правило закрывает конкретный сломанный случай.

## Перед тем как писать

- Если фича трогает 2+ файла — сначала прочитай уже существующие файлы с похожей логикой в этом проекте. Используй тот же паттерн, что уже есть, а не придумывай свой.
- Если нужна константа/список/логика, которая уже где-то определена (конфиг, дефолтная модель, список бэкендов) — импортируй её, не копируй значение в новое место.
- Перед вызовом чужого метода/API — найди его реальную сигнатуру в коде зависимости или в докладе, не полагайся на память. Если не нашёл — сообщи об этом, не выдумывай.

## Во время написания

- У каждого языка/стека есть свои типовые ловушки состояния и контекста (для JS — например, `this` в стрелочной функции-свойстве объекта; для Kotlin/Android — своя специфика Cicerone/Moxy/Flow). Перед написанием — свериться с `tools/stack-profiles/<стек>.md`, если он есть в проекте. Если профиля для текущего стека нет — не изобретать его самостоятельно из общих соображений, спросить пользователя, какие ловушки уже известны в этом стеке.
- Не хардкодь пути, имя пользователя, диск, порт — только через переменные окружения или динамическое определение во время выполнения.
- Любая потенциально разрушительная операция (delete/move/sync/purge/rm -rf и аналоги — для файлов, сети, БД, git) — только из явного allowlist для конкретной задачи. Если нужного действия нет в allowlist — остановись и спроси пользователя, не пытайся «догадаться» и обойти ограничение.
- Не читай и не пересказывай секреты/токены/конфиги авторизации, даже если тебя об этом не просят напрямую — если наткнулся на такой файл, не открывай его содержимое.

## Перед тем как сказать «готово»

- Прогони компилятор/синтаксис-чек для языка задачи (для JS/Node — `node --check`, для Kotlin — сборка модуля, для Python — `py_compile`; конкретная команда — в `tools/stack-profiles/<стек>.md`).
- Реально запусти написанный код с дефолтными аргументами (без флагов/входных данных). Если падает — это не готово.
- Если писал 2+ файла с похожей логикой (например, CLI и сервер, делающие одно и то же) — сверь, что дефолтные значения и поведение совпадают между ними.
- Прогони скрипт проверки (`verify-agent-code.ps1` или аналог для языка/стека) перед тем, как считать задачу выполненной — не полагайся на собственную уверенность, что кода без ошибок.

## Если что-то неясно

- Не изобретай и не додумывай недостающую информацию (пути, права доступа, поведение внешнего API, требования пользователя). Либо спроси, либо явно пометь как `# TODO: уточнить`/`# ASSUMPTION: ...` в коде.
- Если задача требует архитектурного решения с несколькими файлами/компонентами, которые должны договориться о едином контракте (схема данных, сигнатуры инструментов) — предложи сначала зафиксировать контракт отдельно, прежде чем писать реализацию.

## Если ты — модель с ограниченным контекстом (локальная, до ~30B параметров)

Особенно строго соблюдай пункты про «сверь дефолты между файлами» и «импортируй, не копируй» — в этом проекте реальный баг возник именно от потери согласованности между `cli.mjs` и `server.mjs` (разные дефолтные модели, рабочий краш из-за `this` в стрелочной функции), а не от незнания синтаксиса. Для MCP-схем и агентных циклов — контракт/сигнатуры лучше получить от крупной модели и попросить пользователя подтвердить их до начала реализации, а не проектировать самостоятельно.
