# День 14. Инварианты и ограничения состояния

**Видео-демо:** [day14-demo.mp4 на Яндекс.Диске](https://yadi.sk/i/ui9HsqvI5GFbyw) — выбор Qwen3.8-27B через RouterAI, ручной ввод допустимого запроса, явная проверка четырёх инвариантов и аргументированные отказы при конфликтах архитектуры и бизнес-правила.

Ассистент проверяет каждый запрос по отдельному контракту `invariants.json` **до** формирования ответа. Инварианты не входят в историю диалога, загружаются заново для каждого запроса и не могут быть отменены репликой пользователя.

## Что переиспользовано из предыдущих дней

- отдельные домен, хранилище контракта и локальный HTTP-интерфейс — паттерн дней 11–13;
- детерминированная браузерная демонстрация и тесты конфликтных сценариев;
- состояние нового типа не смешивается с диалогом: как task state в дне 13, инварианты имеют собственный источник истины.

## Как работает защита

1. `InvariantStore` читает версионированный JSON-контракт отдельно от сообщений.
2. `InvariantGate` явно проверяет запрос по каждому правилу и формирует trace `passed/conflict` с доказательством.
3. При любом конфликте `InvariantAssistant` возвращает `refused`; генерация решения не выполняется.
4. Отказ называет инвариант, его id, правило и предлагает изменить запрос без нарушения ограничения.

Для разрешённых запросов доступны два режима ответа: детерминированный `Invariant Engine` и реальная модель `qwen/qwen3.8-27b` через RouterAI. В обоих случаях gate выполняется первым; при конфликте внешняя модель вообще не вызывается.

Демо содержит четыре класса ограничений: выбранная архитектура, стек, принятое техническое решение и бизнес-правило.

## Запуск

```powershell
cd day14-state-invariants
python web_server.py
```

Откройте напечатанный адрес. Внешний API и ключи не нужны.

Для ответа Qwen задайте `ROUTERAI_API_KEY`. Без ключа локальный режим и все проверки инвариантов продолжают работать.
