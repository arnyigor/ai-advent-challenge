# День 35: анализ и план AI Release Assistant

Дата исследования: 16 октября 2026. Ниже сохранён первоначальный план.
После выбора пользователя реализован [AI Release Assistant](../day35-release-assistant/README.md):
живой AI-анализ, три успешные проверки, материалы обновления и видео.

## Решаемая задача

Подготовка релиза собственных приложений: из реальных изменений Git получить
понятное пользователю описание обновления, список затронутых областей, рекомендации
по ручной проверке и отчёт о фактически выполненных проверках.

Предлагаемый первый проект — DnsHostsGenerator. Следующий — TaskBridge.
Предположение: регулярная подготовка обновлений полезна владельцу этих проектов.
Частота релизов, затраты времени и личный приоритет пока не подтверждены пользователем.

## Почему DnsHostsGenerator

В проверенном build-apps.yml уже есть:

- запуск по тегам v*;
- Android debug APK: :androidApp:assembleDebug;
- desktop distributable: :desktopApp:createDistributable;
- матрица Windows/Linux/macOS;
- упаковка и прикрепление файлов к GitHub Release.

Новая ценность: подготовка материалов и проверок ДО создания тега.
Текущий Android workflow собирает debug APK; это не публикация подписанного
production-приложения в магазин. Добавление стора/подписи — отдельный объём.

TaskBridge актуальнее по последним изменениям, но охватывает Node-сервер,
клиенты и несколько подсистем. Его CI проверяет Node и KMP JVM; это не означает
проверку сборки Android и всех desktop-пакетов. Он подходит вторым профилем.

## Границы MVP

Вход: путь к локальному репозиторию, явные base/head, профиль проекта, язык.
Base может быть тегом или SHA; при отсутствии тегов пользователь задаёт SHA.
Автовыбор latest release не нужен для первой версии.

Выход:

- evidence.json: SHA, диапазон, изменения, исключения и результаты проверок;
- analysis.json: структурированный ответ модели;
- release-notes.md: черновик описания обновления;
- test-plan.md: рекомендуемые ручные проверки;
- report.html: удобный локальный просмотр результата;
- trace.json: события сбора, генерации и проверки ответа.

MVP не меняет исходный проект, не создаёт тег и не публикует релиз.
Запись результатов — только в отдельную папку запусков.
Второй этап может создать draft release после явного действия пользователя.

## Разделение обязанностей

Детерминированный код:

1. Разрешает refs в неизменяемые SHA.
2. Проверяет, является ли base предком head; при расхождении останавливается
   с понятным предложением явно выбрать другую базу.
3. Читает commit log и diff base..head, фиксирует удаления, переименования,
   бинарные и исключённые файлы.
4. Собирает разрешённые документы и фрагменты с идентификаторами источников.
5. Выполняет только заранее заданные проверки при явном включении их запуска.
6. Фиксирует код выхода, длительность, логи, таймаут и SHA проверки.
7. Проверяет JSON модели и существование ссылок на источники.
8. Вычисляет машинный статус и формирует итоговые файлы.

AI:

1. Группирует изменения по смыслу для пользователя.
2. Объясняет предполагаемое влияние изменений.
3. Предлагает ручные проверки по затронутым областям.
4. Отмечает возможные риски, неопределённость и недостающие данные.
5. Пишет русское описание обновления со ссылками на доказательства.

Модель не определяет фактическое прохождение тестов и не формирует исполняемые
shell-команды. Ссылки подтверждают происхождение, но не гарантируют смысловую
правильность каждого вывода; перед публикацией текст просматривает человек.

## Контракт данных до реализации

Evidence:

- schema_version, run_id, repository;
- base_sha, head_sha, working_tree_dirty;
- commits, changed_files, sources;
- omitted_files, truncated_sources, coverage_complete;
- checks: id, argv, cwd, tested_sha, status, exit_code, duration, log_path.

AI analysis:

- changes: category, title, user_impact, evidence_ids;
- risks: severity, scenario, evidence_ids;
- manual_checks: action, expected_result, evidence_ids;
- uncertainties;
- release_notes.

Статусы проверок: passed / failed / not_run / unavailable / timeout.
Итоговые статусы: blocked / incomplete / checks_passed_review_needed.
Ошибка обязательной проверки даёт blocked; пропуск, устаревший SHA,
неполное покрытие или недоступная модель — incomplete. Даже все пройденные
проверки не превращаются в безусловное обещание готовности релиза.

## Архитектура

CLI и небольшой FastAPI UI используют один orchestrator. Git collector,
check runner, model adapter, validator и renderer разделены по обязанностям.
Для MVP достаточно прямого чтения Git и нескольких разрешённых документов;
векторная база и MCP не являются обязательными для задания дня 35.

Существующие компоненты:

- day32/review.py — образец чтения Git objects и ограничения контекста.
  Не копировать целиком: collect использует merge-base, скрытые директории
  исключены, а для анализа релиза нужен явный диапазон и разрешённые workflow.
- tools/llm — существующий клиент моделей; импортировать общий код, проверив
  фактический интерфейс. Конфигурацию дня 34 не переносить под старым префиксом.
- day34 — образец трассы и UI, но не write/reset инструменты sample_project.
- day34/capture-live-demo.mjs и record_live_video.py — образцы живой записи.

## Надёжность

- Не читать секреты и конфиги авторизации. Корпус ограничивается allowlist.
- README/diff/логи являются данными; инструкции внутри них не исполняются.
- subprocess получает список аргументов, без shell; refs валидируются.
- Сборка проекта исполняет его код: в MVP запускать её только для доверенного
  собственного проекта и только явным действием.
- При включении проверок использовать отдельный checkout head_sha и не
  переносить туда незакоммиченные изменения рабочего каталога.
- Полный diff и бюджет фиксировать до вызова модели; обрезание показывать явно.
- Ошибки модели, пустой/обрезанный ответ и неверный JSON не маскировать успехом.
- Локальная модель и облачный провайдер выбираются явно. Возможность облачной
  обработки исходников показывается до запуска; тихого переключения нет.
- Ключ идемпотентности будущего draft: repository + head_sha + version.

## План реализации

1. Выбрать настоящий диапазон DnsHostsGenerator и сохранить SHA.
   Результат: понятный объём релиза; при пустом diff сообщить отсутствие изменений.
2. Зафиксировать JSON-контракты evidence и analysis, профиль разрешённых файлов
   и проверок. Отдельно указать, что считается обязательной проверкой.
3. Реализовать CLI-сбор фактов и экспорт evidence без вызова AI.
4. Подключить один фактически доступный провайдер, структурированный ответ,
   проверку источников и явную обработку ошибок. Другие провайдеры — после
   первого успешного сквозного прогона.
5. Сформировать release-notes.md, test-plan.md и HTML-отчёт.
6. Добавить минимальный UI с диапазоном, этапами, источниками и статусами.
7. Добавить явный запуск выбранных проверок в checkout точного SHA.
8. Прогнать на настоящем DnsHostsGenerator. Исправить обнаруженные проблемы
   пайплайна, не подменять реальные ошибки проекта успешным статусом.
9. Записать непрерывное демо и оформить README/DEMO/challenge.json дня 35.

Оценка: базовый сквозной MVP примерно один рабочий день; UI, полноценная
приёмка и видео могут потребовать ещё день. Это оценка разработки, не обещание;
время сборок, доступность модели и настройка окружения неизвестны.

## Приёмка

- Один реальный диапазон собственного проекта проанализирован живой моделью.
- Отчёт содержит точные SHA и проверяемые источники.
- Результат использован как реальный черновик описания обновления.
- Неверная ссылка модели отклоняется.
- Отсутствующие/проваленные проверки не получают passed.
- Повторный запуск не меняет рабочие файлы и не публикует ничего автоматически.
- Отдельно проверены: пустой diff, плохой ref, невалидный JSON, таймаут модели,
  неполное покрытие и несовпадение SHA проверки.
- На видео видны ввод, запуск, сбор данных, вызов AI, просмотр доказательств
  и полученные файлы; ожидание ускоряется только с явной подписью.

## Сценарий видео, 2–3 минуты

1. Проблема: несколько приложений, описания обновлений и тест-план вручную.
2. Выбор DnsHostsGenerator и реального диапазона.
3. Запуск: коммиты, diff, источники, явное указание выполненных проверок.
4. Ответ AI: пользовательские изменения и предложенные ручные проверки.
5. Открытие источника для одного конкретного вывода.
6. Сохранённые release-notes.md и test-plan.md; честный итоговый статус.

Формулировка сдачи:

«Автоматизировал подготовку релиза своего приложения DnsHostsGenerator.
Пайплайн собирает реальные изменения Git и результаты проверок, а AI
подготавливает описание обновления, анализ влияния и план ручного тестирования
с привязкой к источникам. Результат — материалы для реального релиза».

## Наблюдение об имеющейся автоматизации сдачи

tools/submit-day.ps1 уже компилирует Python, проверяет секреты, коммитит,
пушит, загружает видео и составляет текст сдачи. По текущему исходнику он
использует git add -A для всего репозитория. Сейчас рабочий каталог содержит
посторонние незакоммиченные изменения, поэтому перед реальной сдачей надо
явно ограничить состав коммита. Скрипт в рамках анализа не запускался.
