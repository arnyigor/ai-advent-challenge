# День 33 — СрокОК и ассистент поддержки

План зафиксирован до реализации, 14 октября 2026.

## Продукт и результат

СрокОК — небольшой журнал гарантий на покупки: название, магазин, дата покупки,
число месяцев гарантии, вычисленная дата окончания, заметка и экспорт JSON.
Без загрузки чеков, оплаты и обещаний отправлять уведомления: это реальные границы v1.
Гарантийный срок в приложении — пользовательская запись, а не юридическое заключение.
Встроенный кабинет поддержки работает с FAQ и контекстом тикета.
Демонстрационные пользователи и обращения явно обозначены; реальные покупки посетителя
хранятся отдельно в его браузерной сессии на сервере.

## Проверенная инфраструктура

Изучены VPS_GUIDE.md и day18-rss-scheduler/VPS_SETUP.md. Существующая капсула
доступна по SSH с прежним ключом; day18-public.service active, порт 8080 занят.
На 14 октября: 1 vCPU, 1902 МБ RAM, около 1534 МБ available; диск 29 ГБ,
26 ГБ свободно. Выделить новому сервису отдельный каталог, venv, SQLite и
systemd-службу. Существующий сервис не перенастраивать.

## Архитектура

Браузер → FastAPI → SQLite (покупки, история) / RAG (Markdown, BM25)
→ MCP stdio-клиент → отдельный MCPServer → JSON с пользователями/тикетами.
После retrieval сервер отправляет только выбранный контекст и историю в Gemini.
Ключ только в переменной среды сервера; браузер его не получает.
Для маленькой базы BM25 с нормализацией русского текста достаточен и не требует
PyTorch или хранения большой embedding-модели на VPS.

## Контракты до кода

- MCP `list_tickets()` → краткие карточки демонстрационных обращений.
- MCP `get_ticket_context(ticket_id)` → ticket, user, related tickets этого пользователя.
  Неизвестный ID возвращает ошибку; JSON читает исключительно MCP-процесс.
- `GET /api/bootstrap` → продукт, MCP-каталог тикетов, индекс документов, модель.
- `GET /api/tickets/{id}` → контекст через MCP, история текущей сессии и этого тикета.
- `POST /api/chat` → `{ticket_id, message}`; история определяется сервером,
  ответ содержит текст, цитаты, найденные источники, трассу MCP и фактическую модель.
- `GET/POST /api/purchases` → список/создание покупки только текущей сессии.
- `GET /api/purchases/export` → JSON только текущей сессии.
- `GET /api/knowledge/{id}` → полный документ для проверки источника.
- `GET /healthz` → readiness базы и индекса; не раскрывает ключи.

Сессия: случайная HttpOnly cookie. Нет выбора чужого пользователя через API.
Demo CRM публична и содержит только вымышленные данные; история ответов и реальные
покупки разделены по cookie. HTTPS через reverse proxy, лимит запросов, очередь
модели, размер сообщений/контекста и таймаут. Ответы/документы выводятся безопасно
как текст; модель не получает инструменты записи или смены статуса аккаунта.

## Интерфейс

Русский интерфейс; две вкладки «Мои гарантии» и «Поддержка».
Продукт: быстрый ввод покупки, понятные показатели, фильтр срока, экспорт.
Поддержка: поиск и список тикетов слева, чат в центре, пользователь и события
справа; стартовые вопросы, загрузка/ошибка с повторной попыткой, источники ответа,
полная статья по клику и раскрываемая MCP-трасса. Мобильная компоновка.

## Порядок реализации

1. Описать продукт, подготовить FAQ и JSON CRM: два разных сбоя входа,
   несохранённая покупка, расчёт месяцев, отсутствие email-уведомлений, экспорт.
2. Реализовать JSON MCPServer и проверить настоящие tools/list и tools/call.
3. RAG: индекс по разделам Markdown, хеш версии корпуса, русский поиск,
   контекст тикета плюс последний вопрос для коротких уточнений.
4. Генерация с ссылками на документы; если нет подходящего документа — честный
   ответ/передача человеку; если API недоступен — ошибка с возможностью повтора.
   Не подменять LLM шаблонным «успешным» ответом.
5. SQLite, API и интерфейс; сохранить историю по сессии + тикету.
6. Проверить изоляцию, инъекции HTML, неизвестный тикет, отсутствие источников,
   даты конца месяца/високосного года, перезапуск, лимиты и отказ провайдера.
7. Реальные запросы Gemini: одинаковый вопрос об авторизации → рекомендации
   из разных MCP-событий; уточнение → продолжение своей истории и цитаты.
8. Развернуть отдельную службу, проверить публичный URL, автозапуск и день 18.
9. Записать непрерывное видео браузера: покупки → тикет → ответ → источники →
   второй тикет → другой ответ → MCP. Сохранить ролик вне Git, README и evidence.

## Приёмка

Реальный продукт создаёт покупки и выгружает их после обновления страницы.
Публичный HTTPS URL доступен; MCP действительно запускается отдельно и отдаёт
данные JSON. Ответ LLM учитывает user/ticket, ссылается на retrieved FAQ;
история разных тикетов и посетителей не смешивается. Видео показывает реальные
сетевые ответы. Всё непроверенное в README обозначено явно.
