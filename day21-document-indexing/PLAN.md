# День 21 — план реализации

## Цель

Построить два воспроизводимых локальных индекса одного корпуса: fixed-size и
structure-aware. В обоих индексах хранятся исходный текст чанка, обязательные
метаданные и нормализованный embedding. Отличается только chunking.

## Корпус

`corpus_manifest.json` выбирает верхнеуровневые Markdown/Python-материалы дней
15–20. Пайплайн самостоятельно считает файлы, слова и эквивалент страниц. Пути
в manifest относительны корня репозитория.

## Контракты

- `Document`: source, title, file, language, text, content_hash.
- `Chunk`: обязательные source/title/file/section/chunk_id, позиция, стратегия и текст.
- `Embedder`: отдельные `encode_documents` и `encode_query`.
- Один SQLite-файл соответствует одной стратегии.

## Сравнение

Фиксируется набор из 12 запросов с ожидаемым source. Для каждой стратегии
измеряются Hit@1, Hit@5, MRR@5, релевантный score, распределение размеров чанков,
число чанков, число embeddings и размер БД. Поиск для сравнения только векторный,
чтобы FTS не скрывал влияние chunking.

## Проверка

1. Корпус содержит 20–35 эквивалентных страниц.
2. У каждого чанка заполнены обязательные метаданные.
3. Chunk ID детерминирован и зависит от стратегии.
4. Количество embeddings равно количеству chunks.
5. Обе БД возвращают результаты поиска.
6. Benchmark работает с одной и той же embedding-моделью.
7. Web UI показывает статистику, чанки и выдачу side-by-side.
