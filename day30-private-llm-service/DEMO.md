# День 30. Сценарий видео

Видео собрано: `ChallengeVideos/day30-demo.mp4`, 110 с (1:50), 1920×1080, без звука, 8 сцен.

Структура рассказа (по одной мысли на сцену, чтобы было понятно «что и зачем»):

1. Зачем: домашняя модель — ещё не сервис; чего хочу и что должен уметь сервис.
2. Решение: шлюз между сетью и моделью, защита в два слоя.
3. Что именно запущено: профиль, почему такой, как запускается.
4. Как это выглядит: **живая съёмка чата в реальном времени** — вопрос набирается по символам,
   нажимается «Отправить», видно ожидание и ответы «Запомнил.» и «КЕДР-42» (61 кадр за 15.55 с).
5. Ключ: без клиентского ключа и без ключа модели — 401.
6. Лимиты: 429, 503, 400, 413 — каждый подтверждён реальным ответом.
7. Проверено на живых запросах: 20 последовательных, 9 одновременных, сбой и восстановление.
8. Выводы: что получилось, что это даёт, чего честно не хватает.

Основная часть — титрированный монтаж по сохранённым реальным ответам API из
`evidence/day30-*.json` (`record_video.py`): ни одна цифра не вводилась вручную, новые
вызовы модели для ролика не выполнялись. Сцена чата — настоящий кадр: headless Chrome
через CDP (`node capture-chat.mjs`) отправил вопросы в работающий шлюз, ответы и строки
с временем, токенами и `request_id` взяты из DOM. Порт шлюза — 8091 (8090 занят Strata).

Длительность регулируется: `python record_video.py --pace 1.0` — спокойный темп (~3 мин),
`--pace 0.62` (по умолчанию) — 1:49, `--pace 0.4` — около 1:10.

Цель: за 4–5 минут показать приватный сервис и доказательства каждого требования. Используется только Qwen3-1.7B Q4_K_M.

## Перед записью

- Прогреть модель коротким запросом. Проверить readiness, alias, CPU, окно 4096 и журнал запуска.
- Подготовить второе устройство в LAN/VPN. Показать метки «сервер» и «клиент», чтобы сетевой запрос был очевиден.
- Завершить полные нагрузочные проверки заранее, открыть сохранённый отчёт. Не смешивать заранее сохранённые результаты с live-запросами без подписи.
- Основной чат и rate-limit демо используют разные ключи. Дождаться чистого окна rate limit, очистить очередь.
- Скрыть ключи, файлы секретов, уведомления и посторонние окна. В примерах показывать $env:SERVICE_API_KEY, без вывода его значения.
- Подготовить короткие вопросы: длинные рассуждения маленькой модели увеличат время видео. Для context-limit использовать генератор запроса и показывать количество токенов, а не весь текст.
- Запись 1920×1080, увеличить шрифт терминала и браузера. Титры или озвучка объясняют ожидаемый результат.
- Кадры чата: `node capture-chat.mjs` (нужен `keys.json`, ключ в кадр не попадает —
  поле ввода типа password). Скрипт делает и посекундную съёмку диалога
  (`video-frames/chatflow/`, ~4 кадра/с, viewport 1280×800 при deviceScaleFactor 1.5),
  и три полноразмерных снимка в `evidence/chat-0*.png`.

## Что должно быть читаемо

Сетевой адрес шлюза, роль второго устройства, alias модели, HTTP-статусы 200/401/429/503, Retry-After, ошибка context_limit, число завершённых запросов, реальные задержки, отсутствие неожиданных ошибок или их честное описание. Одновременный приём запросов не называть одновременной генерацией: backend использует один слот.

Для защиты контекста нужен фактический отказ API, а не только число 4096 в настройках. Для rate limit нужен фактический 429, а не только конфиг. Для сети нужен второй клиент, а не два окна localhost. Для стабильности нужен отчёт серии запросов и успешный запрос после нагрузки.
