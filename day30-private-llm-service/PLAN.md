# День 30. Локальная LLM как приватный сервис

Статус: план реализации, 9 октября 2026. Сервис и проверки дня 30 пока не реализованы. Единственная модель — существующий Qwen3-1.7B-Q4_K_M.gguf. Основной маршрут — текущий Windows-компьютер как домашний сервер. Перенос на VPS для выполнения задания не обязателен.

## 1. Исходная точка дня 29

Изучены README.md, PLAN.md, RESULTS.md, DEMO.md и run-cpu-model.bat дня 29. Проверенный профиль: CPU, 8 потоков, один слот, контекст 4096, temperature=0, max_tokens=1024, reasoning off. Снижение памяти не исправило смысловые ошибки модели. День 30 проверяет доступность и ограничения сервиса, а не новое качество RAG.

Сохраняем профиль исполнения. System prompt RAG из дня 29 не переносим механически в обычный чат: он рассчитан на источники из retrieval. Для чата используем простой prompt с просьбой отвечать кратко на русском и не выдумывать неизвестное. Это новый режим использования, его качество нужно проверить отдельно. RAG и дополнительные модели в обязательную часть не входят.

## 2. Архитектура

```text
Браузер / API-клиент на другом устройстве
               |
       LAN или приватный VPN
               |
    HTTP-шлюз + веб-чат :8091
    Bearer key, rate limit, очередь,
    проверка контекста, таймауты
               |
       127.0.0.1:8081
         llama-server
    Qwen3-1.7B Q4_K_M / CPU
```

8081 — заданный порт модели, 8091 — порт шлюза, задаётся через переменную окружения. Порт 8090 занят другим локальным сервисом (Strata) и не используется. Модель доступна только на loopback. Сетевой интерфейс шлюза задаётся явно: адрес LAN или VPN. Правило Windows Firewall разрешает порт шлюза только выбранному клиенту/подсети. Не делать проброс порта в интернет. Для доступа за пределами дома выбрать приватный VPN; для демо достаточно второго компьютера в LAN. Если нужно HTTPS в LAN, добавить TLS-прокси; Bearer key по обычному HTTP не шифруется.

Предлагаемый стек: Python/FastAPI + httpx, один процесс приложения; HTML/CSS/JS для чата, без внешних CDN. Один экземпляр хранит rate limit и очередь в памяти. Для нескольких workers потребуется общее хранилище, поэтому в этой версии запускать ровно один worker.

## 3. Сначала зафиксировать контракт

Перед реализацией записать API и ограничения в README, затем использовать одни константы для API, UI и проверок.

| Пункт | Предлагаемый контракт |
|---|---|
| GET /health | Готовность backend, без пути к весам и секретов; 503 при недоступности |
| GET /v1/models | Авторизованный запрос, только day30-qwen3-1.7b |
| POST /v1/chat/completions | Bearer key; messages, model, max_tokens; stream=false в первой версии |
| Модель | Фиксированный alias, неизвестная модель → 400 |
| Параметры | temperature=0; thinking off; клиент не переопределяет их |
| max_tokens | Целое число 1–1024; по умолчанию 256; превышение → 400 |
| Контекст | Полный отформатированный prompt + резерв ответа + небольшой запас ≤ 4096 |
| Тело запроса | Не более 64 KiB, превышение → 413 |
| Роли | system задаёт сервер; клиентские user/assistant, текстовые сообщения |
| Rate limit | 10 POST запросов за скользящие 60 секунд на ключ; превышение → 429 + Retry-After |
| Параллельность | Одна активная генерация, максимум три ожидающих; переполнение → 503 + Retry-After |
| Таймаут | Ожидание очереди 60 секунд, генерация 120 секунд; отдельные ошибки queue_timeout / backend_timeout |
| Авторизация | Нет/неверный ключ → 401 до вызова модели |
| Ошибки | JSON error.code, error.message, request_id; без traceback |

Лимит частоты считать для авторизованных POST после проверки схемы, до постановки в очередь; перегруженные запросы тоже расходуют лимит. Неверные ключи не создавать в таблице лимитов. На уровне сети ограничить доступ к шлюзу. Отдельный тестовый ключ нужен для демонстрации 429 без помех основному чату.

max_tokens ограничивает генерацию, а не входной контекст. Считать токены истории с реальным chat template backend, включая system и маркеры ролей. Проверить формат /apply-template и /tokenize на установленной версии, сопоставить счётчик с usage реального запроса. Подсчёт по символам не подходит. Использовать небольшой фиксированный запас, например 32 токена, и проверить граничные случаи. При переполнении вернуть context_limit, ничего не обрезать молча.

Очередь должна оставаться ограниченной и при нескольких одновременных запросах. Освобождать место при ошибке, таймауте и отключении клиента. Не запускать следующую генерацию, пока предыдущая реально занята в backend: истечение HTTP-таймаута само по себе не доказывает отмену inference. Реализацию отмены/готовности проверить отдельно. Последовательно обрабатывать генерации — допустимый способ выдержать несколько запросов; это не параллельное декодирование.

## 4. Запуск модели

Команда для cmd.exe, после проверки свободного порта. Обратные слеши в конце строк из сообщения пользователя не нужны. Эти set-команды не являются синтаксисом PowerShell.

```bat
set "LLAMA_SERVER=G:\AIModels\llamacpp\llama-win-cuda-12.4-x64\llama-server.exe"
set "MODEL=G:\AIModels\SmallAgents\Qwen3-1.7B\Qwen3-1.7B-Q4_K_M.gguf"
set "PORT=8081"
"%LLAMA_SERVER%" -m "%MODEL%" --device none --gpu-layers 0 --no-kv-offload --no-op-offload --ctx-size 4096 --parallel 1 --threads 8 --host 127.0.0.1 --port %PORT% --alias day30-qwen3-1.7b --reasoning off --no-cache-prompt --no-context-shift --n-predict 1024
```

Флаги сверены с --help указанного локального llama-server.exe. Команда здесь — инструкция для будущего запуска, модель при подготовке плана не запускалась. В скриптах пути читать из окружения; проверять существование exe/GGUF и занятость порта. Чужой процесс не останавливать. В журнале загрузки подтвердить CPU и фактическое окно. Не повышать --parallel без отдельной проверки памяти и контекста слота.

## 5. Порядок реализации

1. Создать конфигурацию и README с контрактом. Зафиксировать build/version llama.cpp и SHA-256 GGUF для воспроизводимости. Веса и ключи вне Git.
2. Сделать скрипт запуска модели и readiness-проверку. Он управляет только созданным им процессом. Настройки других локальных LLM не использовать.
3. Реализовать шлюз: проверка ключа и схемы, размер тела, токены, rate limit, ограниченная очередь, backend-запрос, единые ошибки и request_id. Разрешать только предусмотренные маршруты, не проксировать произвольные endpoints llama.cpp.
4. Добавить чат: ввод ключа с хранением только в памяти вкладки, история user/assistant, кнопка «Новый чат», индикатор ожидания, понятные ошибки. В первую версию не включать streaming, чтобы сначала проверить очередь и таймауты. Выводить ответы как текст, не как непроверенный HTML. Не сохранять историю на сервере.
5. Добавить access-лог без prompts, ответов и Authorization: request_id, статус, время ожидания/генерации, usage при наличии. Не включать логирование prompt в llama.cpp; проверить его стандартный stdout на отсутствие содержимого чата.
6. Настроить сетевой bind и ограниченное правило firewall. Проверить HTTP с второго устройства. Не считать запрос на LAN-IP с того же компьютера достаточным доказательством.
7. Выполнить проверки ниже, сохранить результаты. Настроить автозапуск через Windows Task Scheduler с перезапуском после сбоя. После перезапуска ОС подтвердить readiness и сетевой запрос. Это превращает ручной запуск в домашний сервис.
8. Записать видео по DEMO.md. Коммитить код, инструкции и обезличенные доказательства; публикация видео — отдельный завершающий шаг.

План файлов: config.py, app.py, backend.py, limits.py, static/index.html, run-model.bat, run-service.ps1, verify.py, requirements.txt, README.md, PLAN.md, DEMO.md, evidence/. Это будущие файлы, сейчас созданы только PLAN.md и DEMO.md.

## 6. Проверки и критерии готовности

| Проверка | Как выполнить | Критерий |
|---|---|---|
| Локальный backend | /health, /v1/models, короткий chat | Готов, alias совпадает, ответ непустой |
| Сетевой доступ | С другого устройства вызвать API и открыть UI | Реальные 200 и ответ нужной модели |
| Приватный доступ | Запрос без/с неверным ключом, проверка 8081 с клиента | 401; backend недоступен напрямую |
| Чат с историей | «Запомни код КЕДР-42», затем «Какой код?» | История передана; фактический ответ зафиксирован |
| Последовательная нагрузка | 20 коротких запросов, не нарушая 10/min | Все принятые запросы завершены; ошибки и truncation посчитаны |
| Одновременная нагрузка | Три клиента одновременно, три повторения | Девять ответов, нет перепутанной истории; очередь и задержки видны |
| Переполнение очереди | Один длинный запрос, ещё три ожидающих, затем пятый | Пятый получает 503; после освобождения следующий запрос успешен |
| Rate limit | На свежем ключе 11 корректных запросов за 60 секунд | 11-й получает 429, Retry-After; после окна снова 200 |
| Контекст | Запрос ниже границы и выше границы по tokenizer | Допустимый проходит, превышение отклоняется до inference |
| Бюджет ответа | max_tokens=1025 и корректный короткий лимит | 400 при превышении; finish_reason=length показан как обрезание |
| Сбой backend | Остановить только собственный backend и восстановить | Понятная 503, шлюз жив, после старта новый запрос успешен |
| Автозапуск | Перезапуск ОС в согласованное время | Сервис готов без ручного запуска |

Для rate-limit проверки использовать короткую генерацию и дождаться завершения предыдущего запроса, чтобы 429 не смешивался с переполнением очереди. Для нагрузочных прогонов учитывать окно лимита или разные разрешённые тестовые ключи. Очередь тестировать синхронизированно, а не надеяться на случайный порядок HTTP.

Сохранять JSON результатов: время, конфигурация, client/server label, request_id, статус, wall time, queue time, usage, finish_reason, ошибки. Для маленького набора показывать медиану и максимум; p95 имеет смысл только с объяснением размера выборки. Отдельно считать ожидаемые 401/429/503 и неожиданные ошибки. Проверить /health до и после нагрузки. CPU/RSS можно измерить дополнительно, но не выдавать цифры дня 29 за новые измерения.

## 7. Финальный результат

Готовность: модель на домашнем сервере, автозапуск, HTTP API и чат доступны с другого устройства, ключ проверяется, контекст и генерация ограничены, очередь и rate limit воспроизводимо проверены, после нагрузки сервис продолжает отвечать. README содержит команды запуска и воспроизведения проверок. Видео показывает реальные вызовы и ошибки ограничений. Непроверенные пункты помечены явно.

Ориентир: конфигурация и backend — 30–45 минут; шлюз — 2–3 часа; чат — 45–60 минут; сеть и автозапуск — 30–60 минут; проверки — 1–2 часа; видео — 30–60 минут. Это оценка, а не гарантия.

Документация API: https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md . Текущая документация может отличаться от установленного build; при реализации сверять с локальной версией.
