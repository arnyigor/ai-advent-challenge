## Быстрый старт

```bat
:: 1. модель на CPU (loopback 127.0.0.1:8081)
day30-private-llm-service\run-model.bat
```

```powershell
# 2. ключи: один раз создаёт keys.json и model-key.txt (оба вне Git)
..\.venv\Scripts\python.exe verify.py init-keys

# 3. шлюз (один worker), доступен в сети на выбранном адресе
powershell -ExecutionPolicy Bypass -File run-service.ps1 -BindHost 192.168.1.212
```

Проверка: `curl.exe http://192.168.1.212:8091/health` → `{"status":"ok",...}`.
Веб-чат: `http://192.168.1.212:8091/` — ввести ключ (метка `main`) и задать вопрос.

Зависимости: `requirements.txt` (starlette, uvicorn, httpx — уже стоят в `.venv`).

## Ключи доступа

| Источник | Формат | Назначение |
|---|---|---|
| `SERVICE_API_KEYS` | `main=<key>;ratelimit=<key2>` | клиентские ключи, лимит считается по каждому отдельно |
| `keys.json` (по умолчанию, вне Git) | `{"main": "<key>", "ratelimit": "<key2>", "load": "...", "concurrent": "...", "queue": "...", "tests": "..."}` | то же самое, но файлом |
| `MODEL_API_KEY` или `model-key.txt` | строка | ключ самого llama-server (`--api-key`); шлюз отправляет его как `Bearer` |

Без клиентских ключей шлюз не стартует. Ключ модели необязателен: если он задан,
шлюз — единственный держатель, и прямой локальный вызов `/props`, `/v1/models`,
`/v1/chat/completions` на 8081 без него возвращает 401 (проверено). `/health`
модели остаётся открытым для проверки готовности.

После ротации `model-key.txt` перезапустите модель: работающий llama-server держит
старый ключ.

## Контракт API

| Пункт | Реализация |
|---|---|
| `GET /health` | готовность backend, без путей к весам и секретов; 503 при недоступности |
| `GET /limits` | числа контракта для веб-чата |
| `GET /v1/models` | требует ключ, возвращает только `day30-qwen3-1.7b` |
| `POST /v1/chat/completions` | Bearer key; `messages`, `model`, `max_tokens`; `stream=false` только |
| Модель | фиксированный alias, неизвестная модель → 400 `unknown_model` |
| Параметры генерации | `temperature=0`, reasoning off, `stream=false` задаёт сервер; `temperature`/`top_p`/`seed`/`enable_thinking` от клиента → 400 |
| Роли | `system` задаёт сервер; от клиента только `user`/`assistant`, текстовые сообщения |
| `max_tokens` | целое 1..1024, по умолчанию 256; иначе 400 `invalid_max_tokens` |
| Контекст | полный отформатированный prompt + `max_tokens` + запас 32 ≤ 4096; иначе 400 `context_limit` (история не обрезается молча) |
| Тело запроса | ≤ 64 KiB → иначе 413 `payload_too_large` |
| Rate limit | 10 POST за скользящие 60 с на ключ; 11-й → 429 + `Retry-After`; неверные ключи в таблицу лимитов не попадают |
| Параллельность | 1 активная генерация, до 3 ожидающих; 5-й запрос → 503 `queue_full` + `Retry-After` |
| Таймауты | ожидание очереди 60 с (`queue_timeout`), генерация 120 с (`backend_timeout`) |
| Авторизация | нет/неверный ключ → 401 до обращения к модели |
| Ошибки | `{"error":{"code","message","request_id"}}`, без traceback; `x-request-id` в ответе |

Порядок проверок: авторизация → размер тела → схема → rate limit → токены контекста
→ очередь → генерация. Поэтому запросы, отклонённые по схеме, лимит не расходуют,
а превышение контекста и переполнение очереди — расходуют.

Счёт токенов — реальный: `POST /apply-template` рендерит chat template модели,
`POST /tokenize` считает токены её токенизатором. Совпадение с `usage.prompt_tokens`
реального ответа проверено (83 = 83, `evidence/day30-backend.json`). Подсчёт по
символам не используется. `max_tokens` ограничивает генерацию, а не вход.

## Профиль модели

`run-model.bat` (значения заданы жёстко, чтобы машинная переменная `PORT` не сдвинула
модель и не подменилась другая модель):

```bat
set "LLAMA_SERVER=G:\AIModels\llamacpp\llama-win-cuda-12.4-x64\llama-server.exe"
set "MODEL=G:\AIModels\SmallAgents\Qwen3-1.7B\Qwen3-1.7B-Q4_K_M.gguf"
set "PORT=8081"
```

Запуск: `--device none --gpu-layers 0 --no-kv-offload --no-op-offload --ctx-size 4096
--parallel 1 --threads 8 --host 127.0.0.1 --port 8081 --alias day30-qwen3-1.7b
--reasoning off --no-cache-prompt --no-context-shift --n-predict 1024
--cors-origins localhost` плюс `--api-key` при заданном `MODEL_API_KEY`.
Версия: llama.cpp build 11054 (`7d4b92bb9`), `0.4.1-dev`.

Факт из журнала запуска: `n_threads = 8`, `n_slots = 1`, `n_ctx_slot = 4096`, ни одной
строки про CUDA/offload. Модель не запускается, если порт занят, — второй экземпляр
не поднимается.

## Автозапуск

```powershell
powershell -ExecutionPolicy Bypass -File install-autostart.ps1 -Install -BindHost 192.168.1.212
powershell -ExecutionPolicy Bypass -File install-autostart.ps1 -Status
powershell -ExecutionPolicy Bypass -File install-autostart.ps1 -Remove
```

Создаются две задачи на вход в систему (пароль не хранится): `day30-model`
(`run-model.bat`) и `day30-gateway` (через 30 с, чтобы модель успела загрузиться),
с перезапуском до 3 раз при сбое. Логи: `evidence/model-autostart.log`,
`evidence/gateway.log`.

Проверено запуском задач планировщика (не перезагрузкой ОС): модель и шлюз стартуют
задачами, `/health` отвечает. Задачи прогонялись заново после смены порта — состояния
`Ready`, шлюз на 8091 отвечает `{"status":"ok","backend":"ok"}`.

Тонкости, найденные на практике:
- задачи запускают `powershell.exe` полным путём: у планировщика нет в PATH каталога
  `WindowsPowerShell\v1.0`, и короткое имя падает с `0x80070002`;
- `run-service.ps1` пишет свой лог через `Start-Transcript`, потому что перенаправление
  stderr нативной команды в задаче глотает вывод и при `ErrorActionPreference=Stop`
  прерывает запуск;
- повторный `-Install` снимает существующие задачи, а это останавливает уже
  запущенные модель и шлюз — после переустановки запустите их снова;
- если адрес машины в LAN изменился, повторите `-Install -BindHost <новый адрес>`.

## Сеть и доступ со второго устройства

- Шлюз слушает явный адрес (`-BindHost`), модель — только `127.0.0.1`.
- Проброс порта на роутере не делать. Для доступа вне дома — приватный VPN.
- HTTP без TLS: Bearer key не шифруется, для LAN это принято осознанно; при выходе
  за пределы домашней сети нужен TLS-прокси или VPN.
- Правило firewall (нужны права администратора):

  ```powershell
  powershell -ExecutionPolicy Bypass -File allow-firewall.ps1 -RemoteAddress 192.168.1.0/24
  powershell -ExecutionPolicy Bypass -File allow-firewall.ps1 -Status
  ```

  Правило разрешает входящие TCP 8091 только указанной подсети (профили Private, Domain).

Что проверено на самом деле: шлюз отвечает на `192.168.1.212:8091` (health, `/v1/models`
с ключом, 401 без ключа, реальная генерация) и **не** отвечает на `127.0.0.1:8091` —
bind явный. Эти запросы отправлены с того же компьютера, поэтому **доказывают bind,
но не заменяют запрос со второго устройства**. Запрос со второго устройства и
добавление правила firewall в этой сессии не выполнялись: нет прав администратора
(профили firewall включены — Domain/Private/Public) и нет второго устройства.

Что именно подтверждено:

- **Доступ с ключом и без**: 401 без ключа и с неверным ключом до обращения к модели;
  авторизованный `/v1/models` возвращает ровно `day30-qwen3-1.7b`.
- **История**: «Запомни код КЕДР-42» → с переданной историей ответ содержит `КЕДР-42`;
  тот же вопрос без истории — не содержит. Сервер историю не хранит, её передаёт клиент.
- **Последовательная нагрузка**: 20 запросов подряд (пауза 6.2 с, окно лимита
  соблюдено) — все 200, 3 ответа обрезаны по `max_tokens` (`finish_reason=length`),
  ошибок нет; `/health` после нагрузки 200.
- **Одновременные запросы**: 3 клиента × 3 повтора — 9 ответов, каждый со своим
  маркером (`TAG-1xx`), перепутанной истории нет. Это приём запросов, а не
  одновременная генерация: слот один.
- **Очередь**: длинный запрос + 3 ожидающих, 5-й → 503 `queue_full` с `Retry-After: 5`;
  все принятые запросы завершились 200, следующий после освобождения — 200.
- **Rate limit**: 10 запросов прошли, 11-й → 429 `rate_limited` с `Retry-After: 55`;
  после окна тот же ключ снова 200. Отклонённый запрос лимит больше не расходует.
- **Контекст**: prompt 3894 токена + 16 + запас = 3942 ≤ 4096 → 200; prompt 3992 +
  256 + 32 = 4280 > 4096 → 400 `context_limit` за 28 мс, без запуска генерации.
- **Бюджет ответа**: `max_tokens=1` принимается; при задании длинного ответа с
  `max_tokens=16` видно `finish_reason=length` — обрезание видно, а не скрыто.
- **Веб-чат**: два вопроса заданы реальным браузером (headless Chrome → шлюз → модель):
  «Запомни код КЕДР-42» → ответ «Запомнил.», затем «Какой код?» → ответ «КЕДР-42»;
  снимки и строки ответов (время, токены, `finish_reason`, `request_id`) —
  `evidence/day30-chat-ui.json` и `evidence/chat-0*.png`.
- **Сбой backend**: остановка только своего llama-server → `/health` 503 и чат 503
  `backend_unavailable` без traceback, шлюз жив; после запуска — 200.

Юнит-тесты контракта без модели: `python -m pytest tests/test_day30_gateway.py -q`
(34 теста: auth, схема, 413, 429, очередь, таймауты, отсутствие секретов в логе).

## Логи и приватность

- `evidence/access.log` — JSON-строки: `request_id`, метод, путь, статус, метка ключа,
  `total_ms`, `queue_ms`, `generation_ms`, `prompt_tokens`, `completion_tokens`,
  `finish_reason`, код ошибки. Промптов, ответов и заголовка `Authorization` там нет
  (проверено поиском по ключам, меткам и текстам запросов).
- stdout llama-server не содержит текста чата: проверено поиском фрагментов промптов
  по журналам — 0 совпадений, только строки таймингов слотов.
- Веб-чат хранит историю и ключ только в памяти вкладки, ответы вставляет через
  `textContent` (без HTML), внешних CDN нет.

## Ограничения и непроверенное

- Один worker у шлюза обязателен: rate limit и очередь живут в памяти процесса.
- Одна генерация за раз, окно 4096, до 1024 токенов ответа; скорость на CPU —
  порядка 12–20 токенов/с, при пустом prompt-кэше (`--no-cache-prompt`) большие
  истории обрабатываются заметно дольше.
- Качество ответов ограничено маленькой моделью: смысловые ошибки дня 29 не
  исправлены, RAG в этот день не входит.
- **Не проверено**: запрос со второго устройства в LAN; применение правила firewall
  (нет прав администратора); перезагрузка ОС с проверкой автозапуска (задачи
  проверены запуском вручную, перезагрузка не выполнялась); TLS (не настраивался).
- Отмена генерации при отключении клиента: реализована только защита от утечки слота
  очереди; отдельно не измерялась.
