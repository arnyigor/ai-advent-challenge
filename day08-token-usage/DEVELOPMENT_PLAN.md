### Места, которые нельзя просто скопировать без изменения

1. `_trim_to_context()` ограничивает отправляемую историю **символами**
   (`context_chars=24000`). При таком поведении длинная история может незаметно
   отрезаться до того, как запрос достигнет лимита модели.
2. История в памяти и при загрузке ограничена `max_history_messages=50`.
   В SQLite при этом остаются более старые сообщения. Поэтому `agent.history`
   сейчас не обязательно содержит всю сохранённую историю.
3. `_session_usage` начинается с нуля при каждом создании агента.
   SQLite хранит тексты, но не usage: восстановить точный прошлый расход
   токенизацией этих текстов невозможно.
4. Ввод ограничен 8000 символов и в `DefaultInputPolicy`, и в HTML `maxlength`.
   HTTP-сервер принимает JSON до 65536 байт. Эти ограничения приложения могут
   сработать раньше контекстного лимита модели.
5. DeepSeek/Gemini через `ClientProvider` получают историю как текст
   `_conversation_prompt()`: с префиксами ролей и служебными строками.
   Системная инструкция передаётся отдельно. Подсчёт только последней реплики
   или простой суммы содержимого сообщений не измеряет весь запрос.
6. `ClientProvider.generate()` превращает исключения в общий `ProviderError`,
   а агент в конце выдаёт «Ни один LLM-провайдер сейчас не смог ответить».
   Причина переполнения теряется. OpenAI-compatible адаптер также сохраняет
   только HTTP-статус ошибки.
7. Выбор провайдера в `ask(provider_id=...)` отключает переход между провайдерами,
   но `ClientProvider` всё ещё может переключать модели внутри своей цепочки.
   Для сравнения нужен строгий выбор модели без такого переключения.
8. Общий DeepSeek-транспорт уже переносит cache hit/miss в `usageMetadata`,
   однако Day 7 их не включает в `TokenUsage`. Часть других исходных полей usage
   также теряется при преобразовании общего ответа. Это проверить до расчёта цены.
9. `record-video.mjs` Day 7 удаляет `chat_history.db` перед записью.
   Для Day 8 использовать отдельную демонстрационную БД/сессии.
10. Тесты Day 6 импортируют модули с общими именами `agent` и `providers`.
    Простое копирование тестов Day 8 в тот же процесс может проверить модуль
    другого дня из `sys.modules`. Заранее изолировать загрузку тестируемых модулей.

## 3. Какие именно токены считать

Метрики должны иметь однозначный смысл. Состояние «до запроса» измеряется после
нормализации ввода, но до добавления новой пары сообщений в историю.

| Метрика | Определение | Источник |
| --- | --- | --- |
| `current_message_tokens` | Только новое сообщение пользователя после input policy | Токенизатор выбранной модели или явно помеченная оценка |
| `history_tokens_before` | Все сохранённые user/assistant сообщения до текущего запроса | Подсчёт истории в зафиксированном формате |
| `request_tokens_before_send` | Весь фактический вход: system, история, новое сообщение, оформление адаптера | Подсчёт окончательного запроса до отправки |
| `input_tokens` | Вход, учтённый провайдером при текущем вызове | API usage |
| `output_tokens` | Выход, учтённый провайдером | API usage с описанием семантики провайдера |
| `visible_answer_tokens` | Только текст ответа, показанный пользователю | Отдельный подсчёт текста, если выход включает reasoning |
| `total_tokens` | Итог usage текущего вызова | API, либо явно обозначенное вычисление по контракту провайдера |
| `history_tokens_after` | Вся история после добавления успешной пары user/assistant | Повторный подсчёт истории |
| `session_usage` | Сумма известного фактического usage вызовов этой сессии | Сохранённый журнал измерений |

Системный промпт не считать сообщением сохранённой истории. Он входит в полный
запрос. Токены истории и текущей реплики не обязаны в сумме давать ровно токены
запроса: есть system, шаблон диалога и особенности токенизации на границах текста.
Весь подготовленный запрос считать целиком, а не получать сложением карточек.

У результата предварительного подсчёта хранить `count_source`, `is_estimate`
и идентификатор модели/токенизатора. В интерфейсе оценку обозначать `≈`.
Не использовать `len(text) / 4` или чужой токенизатор как точное число токенов.

Если usage не пришёл, показывать «н/д». При наличии локальной оценки показывать
её отдельно. Не превращать её в якобы полученную от API статистику.
Если часть вызовов без usage, общий расход помечать как неполный: существующего
`reported` с логическим OR недостаточно, чтобы утверждать полноту суммы.

Reasoning не прибавлять повторно к `output_tokens` или `total_tokens`, если он
уже включён провайдером. Основное сравнение провести без reasoning, если выбранная
модель позволяет: так проще сопоставить токены ответа и его видимый текст.

## 4. Выбор модели и способа подсчёта

Начать с уже подключённого DeepSeek. До реализации эксперимента проверить для
конкретной доступной модели:

1. Её точный идентификатор и официальный контекстный лимит.
2. Есть ли отдельный лимит входа и как учитывается резерв выходных токенов.
3. Официальный способ предварительного подсчёта: совместимый токенизатор либо
   API подсчёта. Проверить соответствие версии токенизатора версии модели.
4. Формат usage, cache hit/miss, reasoning и признак завершения ответа.
5. Код/тип ошибки при переполнении и возможность автоматического усечения API.

Зафиксировать подтверждённые значения в одном конфиге модели: идентификатор,
лимиты, источник и дата проверки, способ подсчёта. Не переносить лимиты
из названия модели или из настроек Day 7.

Если у основной модели нет доступного точного предварительного счётчика,
разрешается локальная оценка с явной пометкой; итоговый расход брать из usage.
Для воспроизводимой демонстрации можно выбрать другую уже подключённую модель
с подтверждённым счётчиком и меньшим настоящим окном. Все три сценария затем
проводить на одной выбранной модели.

На этапе этого плана текущие лимиты и тарифы внешней документацией не подтверждены:
попытка открыть её завершилась ошибкой соединения. Это отдельный шаг реализации;
готовых чисел в плане намеренно нет.

## 5. Расход и стоимость по мере диалога

Обязательный результат — рост токенов. В задании указано «стоимость/токены»,
поэтому рублёвый/долларовый биллинг не должен задерживать основную реализацию.
Сначала вывести фактические токены по ходам и накопленный расход.

Для каждого успешного хода записывать номер, модель, размер истории до запроса,
вход API, выход API, total, накопленный total и статус. На экране — таблица
и небольшой график: по X номер хода, по Y входные токены; отдельным рядом
показывать накопленный расход. Реализовать обычным SVG без новых библиотек.

Объяснение для README и видео: на следующем ходе история снова отправляется
модели. Поэтому короткий новый вопрос может приводить к большому входу API.
При примерно одинаковых длинах сообщений и без усечения вход растёт примерно
линейно, а сумма входных токенов за N ходов — примерно квадратично.
Это объяснение тенденции, а не обещание одинакового прироста на каждом ходе.

Учебный пример, **не результаты API**:

| Ход | Вход API | Выход API | Всего за вызов | Накоплено |
| --- | ---: | ---: | ---: | ---: |
| 1 | 100 | 20 | 120 | 120 |
| 2 | 140 | 20 | 160 | 280 |
| 3 | 180 | 20 | 200 | 480 |

Размер итоговой истории нельзя подменять последним столбцом: последний столбец
повторно учитывает старую историю при каждом вызове.

Если добавлять денежную оценку, брать подтверждённый тариф конкретной модели
и валюту, сохранять дату и источник. Базовая формула без скидок:

`cost = input_tokens * input_price_per_million / 1_000_000 + output_tokens * output_price_per_million / 1_000_000`

При разных тарифах для cached/uncached input разделять эти категории, не
прибавляя cached tokens сверх уже включающего их input. При отсутствии нужных
данных показывать оценку с описанием допущения либо «н/д». Суммировать стоимость
отдельных вызовов, сохраняя тариф каждого: не пересчитывать всю прошлую сессию
по последней выбранной модели. Не называть расчёт точным счётом провайдера.

## 6. Поведение при переполнении

### Основной режим сравнения

Передавать полную сохранённую историю без скрытого `_trim_to_context()` и без
отбрасывания старых сообщений по количеству. Ограничения размера ввода/HTTP
согласовать с экспериментом и оставить конечными. Если объём слишком велик
для браузерного ввода, наращивать историю через сценарный runner на сервере/CLI,
а результат показывать в web-интерфейсе. Не имитировать старые ответы модели.

В обычном режиме перед отправкой проверять доступный бюджет. Для модели с
общим окном условие имеет вид:

`полный вход + резерв ответа <= контекстное окно`

Отдельные лимиты входа/выхода и reasoning учитывать согласно подтверждённому
контракту выбранной модели. При оценочном счётчике и пограничном запросе не
называть локальное решение точным подтверждением отказа модели.

При локальном превышении вернуть понятный статус `local_context_limit`:
показать оценённый/точный вход, лимит, резерв ответа и источник подсчёта.
Явно написать «Запрос не отправлен». Такой отказ сам по себе ещё не доказывает
переполнение настоящей модели.

### Обязательная демонстрация настоящего ограничения модели

В экспериментальном запуске предусмотреть явный режим отправки без локальной
проверки контекста. Он сохраняет проверку формата и конечные технические лимиты.
Подготовить полный вход больше **настоящего подтверждённого лимита входа**,
чтобы отказ не зависел только от выбранного резерва ответа.

1. Выполнить один такой запрос на той же модели, что в коротком/длинном сценарии.
2. Отключить смену провайдера/модели и повторы для распознанной ошибки контекста.
3. Выделить `ProviderContextLimitError` до преобразования в общий `ProviderError`.
4. Передать UI безопасный структурированный статус `provider_context_limit`,
   модель, HTTP-статус и допустимое описание причины из проверенного ответа.
5. Сохранить фактический результат в журнал эксперимента. Не выводить ключи,
   заголовки авторизации или полное необработанное тело ошибки.
6. Показать, что модель не дала обычный ответ, а новая пара сообщений не появилась
   в сохранённой истории. UI завершает ожидание и остаётся доступным.

Не классифицировать любой HTTP 400 как переполнение: ошибка должна быть
подтверждена кодом/типом/содержанием ответа провайдера. Сетевая ошибка, 429,
ошибка параметров и локальный лимит JSON — отдельные результаты, которые
не засчитываются как демонстрация переполнения модели.

Если API автоматически усекает вход, выяснить возможность отключения усечения;
при невозможности выбрать другую уже доступную модель с явным отказом.
Искусственный маленький лимит приложения допустим для отладки, но не заменяет
этот обязательный эксперимент.

Usage отклонённого/отменённого вызова без данных API неизвестен: нельзя
приписывать ему нулевую стоимость. Отдельно показывать известную сумму и
наличие вызовов с неизвестным расходом. Полученный usage сохранять даже если
ответ впоследствии отклонён выходной политикой, чтобы не терять известный расход.

После демонстрации очистить только тестовую сессию и отправить короткий вопрос.
Успех показывает восстановление работоспособности после уменьшения контекста.
Ошибка ограничения длины **ответа** (`finish_reason=length`/`MAX_TOKENS`) — другое
явление; можно отразить её в метаданных, но не выдавать за переполнение входа.

3. **Реализовать подсчёт.** Отдельно новое сообщение, полная история, полный

   Поддержать источник/оценочность и отсутствие данных.
4. **Расширить хранение.** Добавить журнал запросов с `request_id`, `session_id`,
   порядком хода, моделью, снимком метрик, usage и статусом. Успешную пару
   сообщений и её запись сохранять одной транзакцией. Неуспешную попытку
   сохранять в журнале без фиктивного сообщения assistant.
5. **Восстанавливать статистику.** После перезапуска загружать полную историю
   и накопленные известные расходы из журнала. Счётчик истории пересчитывать
   для выбранной модели. Наличие старых текстов без usage обозначать как
   неполную статистику. `reset` очищает историю и измерения выбранной сессии.
6. **Обработать контекст.** Убрать скрытое усечение из экспериментального пути,

7. **Расширить API и CLI.** `/api/chat` возвращает метрики хода, `/api/history`

   `/api/token-preview` для предварительной оценки без генерации и записи в БД.
   Повторно считать внутри `ask()` под блокировкой: preview может устареть.
8. **Добавить UI.** Карточки «Новое сообщение», «Вся история», «Вход API»,

   по источнику, после — показывать фактический usage. Таблица/график берут данные

9. **Сделать сценарный runner.** Использовать тот же `ChatAgent` и те же

10. **Проверить поведение и записать видео.** Последовательность ниже.

## 8. Три воспроизводимых сценария

Для всех сценариев одинаковые провайдер, модель, system prompt, температура
и лимит выхода. Разные чистые сессии: `day08-short`, `day08-long`,
`day08-overflow`. Записывать дату и фактическую модель каждого ответа.

### A. Короткий диалог

1. «Запомни: код проекта — Маяк-17. Ответь кратко».
2. «Какой код проекта я назвал? Ответь одной строкой».
3. Показать показатели обоих ходов и итоговую историю.

Ожидается: два успешных ответа, измерения входа/выхода; второй запрос включает
первый обмен сообщениями. Реальные значения заранее не подставлять.

### B. Длинный диалог

1. Начать с того же факта, что в коротком диалоге.
2. Выполнить примерно 10–20 обменов: пронумерованные, различающиеся блоки
   нейтрального текста и просьба кратко подтвердить получение.
3. Подобрать объём так, чтобы история заметно выросла и оставалась ниже лимита.
4. Повторить тот же короткий вопрос о коде проекта.
5. Сопоставить короткий вопрос в начале/конце: текст вопроса одинаковый,
   полный вход API и накопленный расход отличаются из-за истории.
6. Показать таблицу всех ходов и график. Ответ на вопрос о факте сохранить
   как наблюдение, не гарантировать безошибочную память любой модели.

Число ходов — ориентир; окончательный объём выбирается по подтверждённому
окну модели. Не заполнять огромное окно десятками дорогих повторных запросов
только ради длительности видео.

### C. Диалог, превышающий лимит модели

1. Создать отдельную сессию с несколькими успешными обменами.
2. Подготовить следующую реплику с воспроизводимым большим блоком так, чтобы
   весь диалог превысил реальный лимит входа; показать расчёт до отправки.
3. При необходимости сначала показать предупреждение локальной проверки.
4. В явном экспериментальном режиме отправить один запрос к API без этой
   проверки, без усечения и без fallback.
5. Показать настоящий отказ из-за контекста, отсутствие обычного ответа и
   неизменность сохранённой истории успешных обменов.
6. Очистить тестовую сессию, задать короткий вопрос и получить успешный ответ.

Для итоговой таблицы сравнения использовать: сценарий, успешные ходы, токены
истории, вход последней попытки (источник указан), выход, известный расход
сессии, статус. Если usage ошибки отсутствует, оставить «н/д», не выдумывать число.

## 9. Проверки при реализации

Сейчас запускать генерации и писать тесты не требуется. После реализации
проверить содержательные случаи:

- Подсчёт кириллицы, латиницы и многострочного текста выбранным счётчиком;
  оценки и точные значения различаются в контракте и интерфейсе.
- Полный вход учитывает system prompt и фактическое оформление адаптера.
- Новое сообщение не попадает в `history_tokens_before` и не считается дважды.
- После успешного ответа история и журнал согласованы; после перезапуска
  восстанавливаются история, таблица и накопленный расход.
- Более 50 сообщений остаются доступными в режиме полной истории; усечение
  по символам не скрывает эксперимент.
- Нет usage / частичный usage / неполная сумма не превращаются в ложные нули.
- Reasoning/cache не считаются дважды; денежную формулу проверить, если включена.
- Проверка бюджета на границе учитывает резерв и правила конкретной модели.
- Локальный отказ не вызывает API; ошибка провайдера не запускает fallback
  и не сохраняет неуспешную пару в историю.
- Сетевая ошибка, 429 и обычный 400 не выдаются за превышение контекста.
- Reset затрагивает только нужную сессию; повтор не дублирует успешные записи.
- Если общий транспорт изменён, его регрессионные тесты и тесты прежних дней
  продолжают проходить. Day 8 тестирует собственные модули, а не Day 6.

После локальных тестов выполнить реальные A/B/C, проверить таблицу в браузере
и восстановление после перезапуска. Моки проверяют логику, но не заменяют
реальное доказательство лимита. Конкретные команды проверки добавить в README
после создания файлов и выбора способа изоляции тестов.

## 10. Сценарий видео

Ориентир — 3–5 минут; продолжительность подстроить под реальные ответы.

| Сцена | Что показать | Что пояснить |
| --- | --- | --- |
| 1 | Чат Day 8, модель, настоящий лимит, названия метрик | Что измеряется и что взято из Day 7 |
| 2 | Два хода короткого диалога | Текущая реплика, история, вход и ответ — разные показатели |
| 3 | Выполнение длинного диалога, таблица и график | Старые сообщения повторно входят в запрос и увеличивают расход |
| 4 | Один и тот же короткий вопрос после длинной истории | Маленькая реплика может требовать большого контекста |
| 5 | Большой вход, лимит модели, реальная ошибка API | Какое именно ограничение сработало и почему ответа нет |
| 6 | Очистка тестовой сессии и успешный короткий запрос | Агент снова работает после уменьшения контекста |
| 7 | Итоговая таблица и ключевые участки кода | Где считаются токены, сохраняется расход и обрабатывается ошибка |

Длинные ожидания можно сократить монтажом с явным обозначением пропуска.
На экране оставить читаемые числа, модель, источник подсчёта и результат.
Титры описывают уже полученные ответы, не обещают успех до завершения запроса.

В рекордере переиспользовать `requireAnswer()` для успешных сцен, а для
переполнения добавить ожидание именно структурированной ошибки контекста.
Проверить и собранный ролик: виден ответ короткого/длинного сценария, рост
чисел, настоящая ошибка и последующее восстановление. Видео хранить вне git.
