# День 9. Управление контекстом: сжатие истории

Агент хранит полный transcript в SQLite, но не отправляет его модели на каждом
ходе. Старые сообщения заменяются rolling summary, а последние `N` сообщений
остаются дословными. Summary хранится отдельно и восстанавливается после
перезапуска.

**Видео-демо:** [day09-demo.mp4 на Яндекс.Диске](https://yadi.sk/i/YtjkBTy07xaPXw) —
48 с, 24 fps: диалог наполняется по ходам, на 16-м сообщении срабатывает сжатие,
затем четыре проверочных вопроса о фактах, которые уже ушли в сводку.

## Запуск

```bash
pip install -r requirements.txt
python web_server.py                 # http://127.0.0.1:8009
python day09_agent.py                # CLI со сжатием
python day09_agent.py --no-compression
python run_comparison.py             # реальный A/B, расходует API-токены
python -m pytest ../tests/test_day9_context_compression.py -q
```

Нужна переменная окружения одного из поддержанных провайдеров. По умолчанию
A/B-runner фиксирует DeepSeek; другой можно выбрать через `--provider`.

## Как работает компрессия

По умолчанию `recent_messages=6`, `summary_batch_size=10`.

1. Полные пары `user/assistant` всегда добавляются в таблицу `messages`.
2. Перед следующим запросом агент проверяет, накопилось ли минимум 10 ещё не
   сжатых сообщений за пределами свежего хвоста.
3. Один пакет и предыдущая сводка отправляются суммаризатору. Новая сводка
   атомарно заменяет прошлую в отдельной таблице `summaries`.
4. Основной запрос получает `system prompt + summary + несжатый хвост + новое
   сообщение`, а не полный transcript.
5. Расход summary-вызова тоже входит в фактический расход сессии. Если
   суммаризатор временно не ответил, агент не теряет сообщения: этот ход идёт с
   ещё не сжатым хвостом.

Исходная история не удаляется. Поэтому интерфейс может показать весь чат, а
алгоритм можно перепроверить или пересобрать с другими настройками.

## Реальное сравнение

`results/comparison.json` получен 10 сентября 2026 года на одном провайдере и
одной модели. В оба режима отправлены одинаковые 8 setup-реплик и 4 контрольных
вопроса. Проверялись код проекта, город, бюджет и формат отчёта.

| Метрика | Полная история | Со сжатием |
| --- | ---: | ---: |
| Качество (верных контрольных ответов) | 4/4, 100% | 4/4, 100% |
| Фактические токены входа | 29 049 | 25 654 |
| Фактические токены выхода | 130 | 630 |
| Фактические токены всего | 29 179 | 26 284 |
| API-вызовы | 12 | 13 (включая 1 summary) |

Итог: сэкономлено **3 395 входных токенов (11,7%)**. Даже с учётом 500
дополнительных выходных токенов суммаризации общий расход снизился на **2 895
токенов (9,9%)**, а качество на четырёх проверках не изменилось.

На короткой истории summary может временно стоить дороже, чем повтор полной
истории. Экономия появляется после амортизации сводки на нескольких следующих
запросах — поэтому A/B использует достаточно длинный, но одинаковый диалог.

## Где смотреть код

- `context_manager.py` — граница свежего хвоста, пакеты по 10, сборка контекста.
- `agent.py` — summary-вызов перед ответом, метрики и fallback без потери данных.
- `history_store.py` — раздельные таблицы полного transcript и summary.
- `run_comparison.py` — воспроизводимый тест качества и расхода токенов.
- `web_server.py`, `web/` — чат и наглядные метрики до/после.
- `record-video.mjs` — автоматическая запись ролика: реплики берутся дословно из
  `comparison.db`, метрики — из `results/comparison.json`. Обе вещи создаёт
  `run_comparison.py`, поэтому перед перезаписью видео нужно прогнать его.

Локальные значения с `≈` — языковая оценка из Дня 8. Итоговая таблица использует
только `usage`, который вернул провайдер.
