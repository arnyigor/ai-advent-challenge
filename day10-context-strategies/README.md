# День 10. Управление контекстом: разные стратегии (без summary)

Агент хранит полный transcript в SQLite и переключается между тремя способами
решить, что именно уйдёт в модель. Сжатия истории (Day 9) здесь нет ни в одном
режиме.

**Видео-демо:** [day10-demo.mp4 на Яндекс.Диске](https://yadi.sk/i/-I8zIQPfNmmwlA) —
90 с, 24 fps: один сценарий «собираем ТЗ» прогоняется тремя стратегиями подряд.
Sliding Window теряет все пять фактов (0/5), Sticky Facts держит их в панели
памяти (5/5), затем checkpoint, две ветки от одной точки и переключение между
ними.

| Стратегия | Что уходит в запрос |
| --- | --- |
| **Sliding Window** | последние `N` сообщений, остальное отбрасывается |
| **Sticky Facts** | блок «ключ: значение» + последние `N` сообщений |
| **Branching** | вся история активной ветки диалога |

## Запуск

```bash
pip install -r requirements.txt
python web_server.py                          # http://127.0.0.1:8010
python day10_agent.py --strategy facts        # CLI
python day10_agent.py --strategy branching
python run_strategies.py                      # реальный прогон, расходует API-токены
python -m pytest ../tests/test_day10_strategies.py -q
```

Нужна переменная окружения одного из поддержанных провайдеров. Runner по
умолчанию фиксирует DeepSeek; другой выбирается через `--provider`.

## Как работает каждая стратегия

### 1. Sliding Window

`build_context` берёт `history[-N:]`. Всё, что старше, просто не попадает в
запрос — но остаётся в базе, поэтому интерфейс показывает весь диалог.
Дополнительных вызовов модели нет.

### 2. Sticky Facts / Key-Value Memory

Перед каждым ответом делается отдельный вызов-извлекатель: текущая память плюс
новая реплика пользователя → JSON `{"ключ": "значение"}`. Апдейт мержится в
таблицу `facts`, и уже обновлённый блок уходит в основной запрос вместе с
последними `N` сообщениями.

Память **только дополняется и перезаписывается**. Удаление факта пустой строкой
в первой версии было — и оказалось footgun'ом: модель периодически «прибирала»
факты, которые считала неактуальными, и код проекта молча исчезал из памяти
(4/5 на контрольных вопросах). После запрета удаления — 5/5.

### 3. Branching

Ветка знает родителя и `fork_index` — сколько родительских сообщений она
унаследовала. История ветки собирается как `история_родителя[:fork_index] +
собственные сообщения`, поэтому checkpoint не копирует диалог. Факты при
создании ветки наследуются от родителя, дальше живут независимо.

Checkpoint — это просто текущая длина истории ветки. От одной точки можно
создать сколько угодно веток и переключаться между ними без потери любой из
них.

## Реальное сравнение

`results/strategies.json` получен 11 сентября 2026 года на одном провайдере и
одной модели. Каждая стратегия прошла один и тот же сценарий «собираем ТЗ»:
12 setup-ходов (первые пять несут факты — код `Ирбис-4`, Android, 640 000 ₽,
15 декабря, PDF), затем 5 контрольных вопросов об этих фактах. При `N = 6`
факты к моменту проверки заведомо вышли за окно.

| Метрика | Sliding Window | Sticky Facts | Branching |
| --- | ---: | ---: | ---: |
| Качество (верных ответов) | 0/5 | 5/5 | 5/5 |
| Токены входа | 5 694 | 13 242 | 10 201 |
| Токены выхода | 336 | 413 | 345 |
| Токены всего | 6 030 | 13 655 | 10 546 |
| API-вызовов | 17 | 34 | 17 |
| Из них вызовов памяти | 0 | 17 | 0 |

Ветвление проверено отдельным сценарием: checkpoint на 6 сообщениях, две ветки
от одной точки, по одному ходу в каждой. После переключения ветка `mobile`
отвечает «приложение», ветка `web` — «кабинет», общий префикс у обеих одинаков,
чужих сообщений не видит ни одна (`isolated: true`, 2 538 токенов на 7 вызовов).

### Выводы

**Качество.** Sliding Window провалил все пять вопросов — он не «забывает
частично», а отбрасывает начисто. Facts и Branching дали по 5/5.

**Стабильность.** Branching стабилен по построению: он ничего не теряет, пока
история влезает в контекст. Facts стабильны ровно настолько, насколько надёжен
извлекатель, — и его ошибки тихие, как показал случай с удалением по пустой
строке.

**Расход токенов.** На диалоге из 17 ходов Facts оказался самым дорогим:
13 242 входных токена против 10 201 у полной ветки. Причина — удвоенное число
вызовов: каждая реплика пользователя стоит двух запросов, и в каждом
извлекателе едет весь блок памяти. Sliding Window дешевле полной истории на
44,2%, но платит за это нулевым качеством.

Facts выигрывают по цене не на 17 ходах, а там, где полная история перестаёт
влезать в окно: у Sliding Window и Facts запрос на последнем ходе стоит ≈292 и
≈391 токена и **не растёт**, у Branching — ≈593 и растёт линейно. Здесь
диалог просто слишком короткий, чтобы линейный рост успел обогнать постоянную
доплату за извлекателя.

**Удобство.** Sliding Window не требует настройки вообще. Facts дают видимое
состояние: пользователь смотрит на панель и понимает, что агент про него
запомнил. Branching — единственный режим, где можно проверить два варианта
решения, не потеряв ни один, но его нужно вести руками: создать ветку,
переключиться, помнить, где ты находишься.

## Где смотреть код

- `strategies.py` — три стратегии, key-value память и разбор ответа извлекателя.
- `agent.py` — переключатель стратегии, вызов памяти перед ответом, метрики.
- `history_store.py` — ветки (`parent_branch_id` + `fork_index`), facts, transcript.
- `run_strategies.py` — воспроизводимый прогон одного сценария по трём стратегиям.
- `web_server.py`, `web/` — чат, переключатель, панель facts и дерево веток.

Локальные значения с `≈` — языковая оценка из Дня 8. Итоговая таблица
использует только `usage`, который вернул провайдер.
