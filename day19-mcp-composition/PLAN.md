# День 19 — композиция MCP-инструментов: план до разработки

## Цель и границы

Сделать один локальный MCP-сервер, который объявляет три отдельных инструмента: `search`, `summarize`, `saveToFile`. Один клиентский запуск автоматически вызывает их в этом порядке через MCP `tools/call`, передавая структурированные результаты без ручного копирования. Результат — сохранённый файл, исходный код и видео реальной цепочки.

Под «в рамках одного MCP» понимаем один MCP-сервер и одно клиентское соединение на весь запуск. Это сохраняет смысл задания про композицию **нескольких инструментов**. Оркестрация находится в клиенте: так в трассе видны три независимых вызова. Если требование буквально означает один экспортируемый `mcp-tool`, контракт нужно изменить до реализации: тогда внутри него будут три этапа, но показать композицию отдельных MCP-инструментов через `tools/call` уже нельзя.

## Связь с предыдущими днями

- День 16: оставить официальный Python MCP SDK, `initialize`, `tools/list`, stdio и проверку схем через настоящее соединение.
- День 17: взять структуру небольшого MCP-сервера, детерминированного клиента, локального веб-интерфейса и запись видео через Chrome/ffmpeg. Не копировать его Git-специфику.
- День 18: можно использовать локально сохранённые материалы как источник, но не связывать работоспособность дня 19 с RSS, планировщиком, SQLite или VPS. Для воспроизводимого демо нужен небольшой фиксированный набор данных, включённый в код дня 19.

## Контракт данных (зафиксировать перед реализацией)

Все три инструмента живут в одном сервере. Результаты — JSON-объекты; у каждого есть `run_id`, чтобы UI и проверки могли сопоставить этапы одного запуска.

| Инструмент | Вход | Выход | Обязанность |
|---|---|---|---|
| `search` | `query: str` | `run_id`, `query`, `items: [{id, title, text, source}]` | Найти материалы в локальном фиксированном корпусе. |
| `summarize` | `run_id: str`, `query: str`, `items: list` | `run_id`, `query`, `summary`, `source_ids`, `source_count` | Сделать краткую сводку только по переданным элементам. |
| `saveToFile` | `run_id: str`, `query: str`, `summary: str`, `source_ids: list` | `run_id`, `path`, `bytes_written` | Сохранить итоговый UTF-8 файл в выделенный каталог дня 19. |

Перед написанием кода проверить точные типы и форму `structured_content` в установленной версии SDK; клиент должен явно валидировать выход каждого этапа перед следующим вызовом. Идентификаторы источников и `run_id` должны проходить цепочку без замены. Пустой результат поиска и ошибки записи обрабатывать явно.

## Поведение и безопасность

1. `search` работает по встроенному локальному корпусу, чтобы запуск без ключей, сети и внешних сервисов давал одинаково проверяемую цепочку. Тема корпуса — материалы проекта про MCP; точный набор утвердить при реализации.
2. `summarize` детерминированно сжимает найденное; внешняя LLM не требуется для демонстрации композиции. В UI назвать это алгоритмической сводкой, а не выдавать за ответ модели.
3. `saveToFile` сам формирует безопасное имя по `run_id` и пишет только в каталог результатов дня 19. Клиент не передаёт произвольный путь. Предыдущие результаты не удаляются и не перезаписываются незаметно.
4. Один сценарий CLI запускается без аргументов с демонстрационным запросом; веб-интерфейс вызывает тот же клиентский пайплайн. Все три шага идут автоматически после одной команды или одного нажатия.
5. При ошибке этапа цепочка останавливается, файл не создаётся, а пользователю показывается конкретный неуспешный этап.

## Последовательность работы

1. Создать `day19-mcp-composition/` и проверить API официального SDK 2.2.0 в текущем окружении. Зафиксировать окончательные сигнатуры инструментов и JSON-контракт.
2. Реализовать сервер и локальный корпус. Проверить настоящий `tools/list`: один сервер объявляет ровно три инструмента с корректными схемами.
3. Реализовать клиент: открыть одну stdio-сессию, вызвать `search`, передать `items` в `summarize`, передать `summary` и `source_ids` в `saveToFile`, закрыть сессию. Записать трассу аргументов и ответов каждого `tools/call`.
4. Добавить CLI и локальную веб-страницу с одной кнопкой запуска. Показать запрос, три этапа, вход и выход каждого, конечный путь и содержимое файла. Проверить, что UI не инсценирует ответы, а отображает трассу настоящего MCP-клиента.
5. Написать интеграционные проверки с реальным дочерним MCP-процессом: порядок трёх вызовов; равенство `items` между первым и вторым этапами; равенство `summary` между вторым и третьим; совпадение содержимого файла с итогом; пустой поиск; отказ записи; отсутствие выхода за выделенный каталог.
6. Выполнить `py_compile`, запуск CLI с аргументами по умолчанию, тесты дня 19 и общий набор тестов проекта. Проверить веб-сценарий вручную.
7. Записать короткое MP4: каталог трёх инструментов → один запуск → последовательное появление трёх вызовов → сравнение переданных данных → открытие сохранённого файла. Проверить воспроизведение и контрольные кадры. Подготовить README с командами и ссылкой на видео.

## Артефакты и критерии готовности

- Код сервера, клиента, веб-интерфейса и скрипта записи — в `day19-mcp-composition/`.
- Проверки — в `tests/test_day19_mcp_composition.py`.
- Видео — `ChallengeVideos/day19-demo.mp4` (как у предыдущих дней, локальный файл может быть исключён из Git).
- Одна команда/кнопка запускает всю цепочку без ручного переноса данных; сервер объявляет три отдельных инструмента; итоговый файл содержит сводку именно тех данных, которые вернул `search`.

## VPS

Не нужен. Stdio MCP-сервер, клиент, корпус, веб-страница и запись видео работают локально. VPS понадобился бы только для отдельного требования о круглосуточной работе или публичном URL, которого в задании дня 19 нет.

## Уточнение после первой демонстрации

Пользователь попросил явно показать модель. Поэтому `summarize` теперь вызывает Gemini 3.5 Flash при доступном `GEMINI_API_KEY`; при недоступности модели результат помечается как локальная сводка. Фактически использованные режим и модель проходят в `saveToFile`, отображаются в интерфейсе и записываются в TXT. Видео перезаписано с подтверждённым ответом `gemini-3.5-flash`.
