# Аудит и завершение дня 34

## Анализ задания и предыдущих дней

День 31 дал локальный интерфейс, работу с документацией и настоящий MCP; день 32 —
анализ кода и diff; день 33 — видимую трассу инструментов и работу модели с контекстом.
Для дня 34 нужен следующий шаг: решение о чтении и записи принимает модель,
а приложение выполняет выбранные файловые операции и возвращает результат в цикл.
Здесь не нужны VPS, публичный домен, RAG-индекс или база пользователей:
корпус небольшой, прямой поиск и чтение дают проверяемые источники без индексации.

Реализация уже содержала отдельный MCP-процесс, шесть инструментов, UI, три цели,
эталон проекта, тесты, приёмку и ролик. Переписывать это заново не требуется.
Модель получает настоящий tools/list, выбирает вызовы, видит результаты и ошибки.
Зашитые сценарии задают только цель: последовательность инструментов не задана.

## Провайдер и расходы

MCP, веб-сервер и файлы работают на компьютере. Gemini — облачная генерация,
поэтому это локальное приложение с внешней моделью, а не полностью офлайн.
Для бесплатного Gemini нужен ключ проекта Free Tier без подключённого биллинга
и доступная этому проекту модель. Название модели само по себе не гарантирует
бесплатность: https://ai.google.dev/gemini-api/docs/billing/ и
https://ai.google.dev/gemini-api/docs/pricing . Приложение не проверяет тариф ключа.
При исчерпании квоты показывается ошибка; автоматического платного fallback нет.

Полностью локальный вариант уже поддержан через LOCAL_LLM_URL и LOCAL_LLM_MODEL.
Он совместим с сервером, предоставляющим /v1/chat/completions. Wormsoft отдельно
не интегрирован: в репозитории нет его подтверждённого API-контракта. Если это
локальный OpenAI-совместимый сервер, используется тот же адаптер local.
OpenRouter ограничен free-именами моделей; для минимальной сдачи он не требуется.

## Что исправлено при аудите

1. MCP search_files теперь передаёт max_results в реализацию.
2. Явный end_line больше не обходит ограничение 400 строк; обратный диапазон отклоняется.
3. write_file проверяет старый файл: бинарные и слишком большие файлы не перезаписываются.
4. Итоговый diff повторно вычисляется после последнего действия модели; ошибка diff
   больше не маскируется пустым списком изменений.
5. Блокирующая генерация выполняется в потоке, не блокируя asyncio MCP-клиента.
6. Сброс отклоняет пересекающиеся каталоги baseline/project и корень репозитория;
   HTTP-блокировка держится до завершения сброса.
7. Отклонены Windows alternate data streams; атомарная запись использует уникальный tmp.
8. Приёмка проверяет чтение кода и CHANGELOG до записи, расположение записи внутри
   Unreleased и исправление вызова total в README; полные трассы сохраняются отдельно.
9. Bootstrap и health используют настроенные корни. Health проверяет каталог;
   соединение с MCP реально проверяется через bootstrap.

session_diff сравнивает с постоянным baseline, а не со снимком начала каждого
запроса. Перед независимым сценарием нужен reset. Сброс предназначен для выделенной
демо-копии: он удаляет её содержимое и восстанавливает эталон.

## План завершения и проверок

Сначала регрессионные тесты, затем три настоящих модельных прогона через MCP,
проверка отчёта и сохранённых трасс. Для видео — цель, чтение исходников,
точечная правка и крупный diff. Уже записанное видео показывает реальную работу;
это монтаж снимков браузера, ожидание сокращено и подписано. Оно без озвучки.
Для повторной записи предусмотрены capture-demo.mjs и record_video.py,
для опциональной локальной озвучки — generate_narration.py.

Успех на трёх целях не доказывает корректность произвольных изменений. Diff
остаётся основным способом проверить результат. Имена файлов не защищают от
секретов внутри обычного исходника; в демо используются только учебные данные.

Дополнительно: сетевой сбой после записи теперь показывает частичный diff в UI.
Регрессионный тест проверяет сохранение файла и diff при обрыве генерации.
