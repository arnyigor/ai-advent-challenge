# День 18 — Habr RSS по расписанию

**Видео-демо:** [day18-demo.mp4 на Яндекс.Диске](https://yadi.sk/i/LWiKXs55n0xgCA) — публичный URL работающей капсулы, сохранённые статьи и сводка, расписание и скачивание TXT.

Сборщик читает RSS хаба «Искусственный интеллект», сохраняет новые публикации в SQLite и формирует сводку. MCP-инструмент `get_habr_digest` отдаёт последнюю сохранённую сводку и состояние сборщика. Сборщик и генератор — короткие одноразовые процессы; на VPS их запускают таймеры.

## Публичная проверка работающей капсулы

**URL:** [http://176.53.175.196:8080/](http://176.53.175.196:8080/)

**Видео по URL:** [http://176.53.175.196:8080/demo.mp4](http://176.53.175.196:8080/demo.mp4)

На странице видны число сохранённых статей, последний сбор, время следующих запусков, полная сводка без модели, ссылки на RSS-публикации и журнал сборов. Кнопка **«Скачать TXT»** отдаёт сохранённую сводку отдельным файлом. Страница обновляет данные каждые 30 секунд. Для открытия не нужны SSH, учётная запись или API-ключи.

Публичный процесс `public_server.py` работает как отдельная служба `day18-public.service` на порту 8080 и читает SQLite в режиме `mode=ro`. Он предоставляет только `GET /`, `GET /api/state`, `GET /digest.txt`, `GET /healthz` и три статических файла, включая видео. `POST` возвращает HTTP 405; база и секреты через URL не выдаются. Текущий адрес использует HTTP; для HTTPS понадобится домен или подходящий способ выдачи сертификата. Это отдельный интерфейс для проверяющих; локальная панель ниже содержит кнопки ручного запуска и сброса.

Видео публичной проверки: `node day18-rss-scheduler/record-public-video.mjs` → `ChallengeVideos/day18-demo.mp4`. В нём показываются настоящий URL, состояние базы, расписание, сводка, журнал и клик по скачиванию TXT. При смене адреса задайте `DAY18_PUBLIC_URL` перед запуском скрипта. Запись сохраняется локально; публикация на Яндекс.Диске выполняется отдельно.

## Локальный запуск

```powershell
python -m pip install -r day18-rss-scheduler/requirements.txt
python day18-rss-scheduler/worker.py collect
python day18-rss-scheduler/worker.py digest
python day18-rss-scheduler/rss_mcp_server.py
```

Последняя команда запускает MCP по stdio и ожидает клиента. Для базы в другом месте задайте `DAY18_DB_PATH` в окружении обоих процессов.

Для сводки строго без модели задайте `DAY18_DIGEST_MODE=plain` перед запуском `worker.py digest` или планировщика. В этом режиме нет вызовов провайдеров и не нужны API-ключи; ссылки и выдержки берутся из RSS.

Цепочка генерации: Gemini `gemini-3.7-flash` → Gemini `gemini-3.5-flash` → OpenRouter `qwen/qwen3.8-27b:free` → Wormsoft `qwen/qwen3.8:27b` → резервный Gemini `gemini-2.5-flash` → сводка из RSS без модели. Ключи: `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, `WORMSOFT_API_KEY`. `WORMSOFT_BASE_URL` необязателен. Значения ключей не сохраняются в SQLite и не печатаются. В базе сохраняются названия попыток и безопасные типы ошибок.

Проверка цепочки: `python -m pytest tests/test_day18_rss_scheduler.py -q`. Она подменяет ответы провайдеров и проверяет порядок переходов без расхода квоты. Реальные вызовы проверяются отдельно. Перед сдачей `python -m pytest tests -q`: **296 passed**.

Локальная панель без фоновых запусков: `python day18-rss-scheduler/web_server.py`. Для **короткого расписания демо**:

```powershell
python day18-rss-scheduler/web_server.py --demo-schedule --collect-seconds 6 --digest-seconds 45
```

Пока этот процесс запущен, он сам собирает RSS каждые 6 секунд и пытается создать новую сводку каждые 45 секунд. Панель показывает время следующего запуска и исход предыдущего. Если с прошлой сводки новых публикаций нет, генерация пропускается. Для отдельного фонового процесса без панели: `python day18-rss-scheduler/scheduler.py --collect-seconds 6 --digest-seconds 45`. Закрытие локального процесса останавливает расписание.

Кнопка **«Сбросить демо»** очищает только локальную базу дня 18: статьи, журнал загрузок и сводки. Параметры активного расписания сохраняются, и следующий плановый сбор заполнит базу снова. Панель показывает число полученных RSS-элементов, число новых записей и журнал последних загрузок. Локальная база проекта была сброшена после добавления этой функции; при запуске без расписания она пуста до нажатия «Собрать RSS».

Локальное видео: `node day18-rss-scheduler/record-video.mjs`; нужны Node.js 22+, Chrome и ffmpeg. Без дополнительных настроек ролик использует реальный RSS и эмулированные отказы моделей, явно обозначенные в панели. Для записи с ранее сохранённой **реальной** модельной сводкой укажите путь к её SQLite в `DAY18_VIDEO_SEED_DB`. Эта запись показывает два автоматических сбора, расписание следующей сводки и реальный сохранённый ответ Gemini 3.5. Золотая рамка выделяет текущий элемент интерфейса. MP4 сохраняется в `ChallengeVideos/day18-local-schedule-demo.mp4` и исключён из Git.

Отдельное видео загрузки и сброса с пустой базой: установите `DAY18_VIDEO_MODE=reset` перед запуском `record-video.mjs`. Оно создаёт `ChallengeVideos/day18-reset-demo.mp4` (около 27 секунд): 0 статей → 40 получено и 40 новых → сброс → повторная загрузка. Перед каждым нажатием кнопка подсвечивается золотой рамкой, курсор перемещается на неё и выполняет настоящий клик. Затем подсвечиваются изменившиеся счётчики и журнал. Видео сохраняются локально; эти команды не загружают их в облако.

Локальная проверка 23.09.2026: RSS вернул 40 публикаций; короткие запросы ответили через Gemini 2.5, OpenRouter и Wormsoft 27B. В первом длинном запросе Gemini 3.7/3.5 ответили HTTP 503, OpenRouter Qwen — HTTP 429, Wormsoft — таймаут; сохранилась расширенная сводка из RSS. При повторной проверке Gemini 3.7 дал HTTP 503, а Gemini 3.5 создал реальную сводку длиной 7047 символов. Интеграционные тесты проверяют переключение провайдеров, расписание и вызов `get_habr_digest` через отдельный MCP-процесс. Для Wormsoft каталог моделей не сообщает цену, поэтому перед длительным запуском на VPS нужно подтвердить бесплатный режим в аккаунте провайдера.

## Работающая капсула Ubuntu 24.04 LTS

Данные подключения, команды проверки и схема файлов: [VPS_SETUP.md](VPS_SETUP.md). На капсуле работают два `systemd`-таймера: сбор каждые два часа и сводка без модели ежедневно в 09:00 по Екатеринбургу. Первый запуск сохранил 40 RSS-публикаций и сводку из 10 материалов. Вызов `get_habr_digest` через SSH-процесс проверен: он вернул сохранённую сводку.

На VPS установлены два `systemd` oneshot service и timer. Оба запускают `worker.py` с абсолютным путём к Python в виртуальном окружении и общей `DAY18_DB_PATH`. `Persistent=true` выполняет пропущенное задание после перезагрузки. MCP-сервер можно запускать через SSH и stdio из клиента; открытый публичный HTTP-порт не требуется.
