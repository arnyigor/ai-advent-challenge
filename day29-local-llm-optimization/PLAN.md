# День 29: подробный план

## Исполненный результат

Выбран ресурсный профиль compact: Q4_K_M, temperature=0, max_tokens=1024, окно 4096, исходный system prompt, CPU/8 потоков/reasoning off. Три повтора на шести вопросах дали 18 необрезанных ответов, полностью совпавших с temperature=0/окно 8192. Измеренный пик RSS уменьшился с 4024 до 3576 MiB, качество осталось 0,67/2, ускорения нет. Подробный system prompt отклонён из-за неподтверждённых фактов после отказа; первичная завышенная оценка исправлена. Проверен и обычный CLI ask.py на выбранном сервере. optimized.json содержит полный prompt, SHA-256 и ссылки на доказательства; подробные итоги в RESULTS.md. Ниже сохранён план и порядок гипотез, включая отклонённые варианты.

## Оптимизация температуры и system prompt

По запросу пользователя проверены отдельно temperature=0.1/0 на исходном prompt и на коротком русском шаблоне, max_tokens=4096 везде: 4 профиля × 6 вопросов × 1 повтор. На исходном шаблоне снижение температуры не исправило смысловые ошибки. Короткий русский шаблон на ложной предпосылке неправильно объявил подтверждение оператора необязательным, поэтому отклонён независимо от средней оценки.

Проверены дополнительные гипотезы: требования дословной цитаты (фаза остановлена во время MCP-генерации после более 1000 токенов повторений, завершённые четыре вызова сохранены с aborted=true) и короткие английские инструкции с русским ответом (по три контрольных вопроса × две температуры). Они дали ошибки ссылок, выдуманные факты и повторение шаблона; не используются в выбранной конфигурации. Прерванный прогон нельзя сравнивать с полным набором по его медиане.

Итоговое подтверждение — baseline и focused-control, 6 одинаковых вопросов × 3 повтора × 2 профиля = 36 вызовов в одном сервере. У обоих temperature=0.1 и max_tokens=4096; различается только system prompt. Модель Q4_K_M, окно 8192, CPU/8 потоков/reasoning off неизменны. Между повторами порядок профилей меняется. cache_n и cached_tokens проверяются по сохранённым метаданным, чтобы не приписывать эффекту prompt выигрыш от кеша. В этом прогоне ресурсы процесса сохраняются для каждого запроса отдельно.

Промпт focused-control использует CPU_FOCUSED из кода: разбить составной вопрос на части, ответить по доступным фактам, не отказать на всё из-за одной отсутствующей части, сохранить условия, исправить ложные предпосылки, отметить границы доказательств. Результат выбирается по фактическим ответам, а не названию профиля или успешному HTTP. Сохранённые параметры и полный текст prompt фиксируются в optimized.json; ask.py читает этот файл с проверкой SHA-256. Старые результаты и неудачные варианты сохраняются. Итоговые цифры и ограничения публикуются в RESULTS.md после завершения всех повторов.

Область проверки — только шесть вопросов, на которых также выбирались промпты. Это не независимый holdout. Улучшение полноты или средней оценки не означает устранение ошибок в сложных RSS/MCP-вопросах; такие ошибки должны остаться видимыми в финальном отчёте.

## Актуальный маршрут: небольшая модель на CPU

По уточнению пользователя основной эксперимент переносится на Qwen3-1.7B. Большая Strata не нужна и остаётся работающей. Текущий файл Q4_K_M проверен SHA-256: это unsloth/Qwen3-1.7B-GGUF, ревизия d7f544eead698dbd1f15126ef60b45a1e1933222. Из той же ревизии скачиваются Q2_K (777796160 байт) и Q8_0 (1834426944 байт); Q4_K_M (1107409472 байт) переиспользуется. Источник: https://huggingface.co/unsloth/Qwen3-1.7B-GGUF/tree/d7f544eead698dbd1f15126ef60b45a1e1933222 . Все файлы проверяются по SHA-256 из metadata Hugging Face.

Порядок: сохранить retrieval → три квантования с одинаковым baseline, окном 8192, thinking off, 8 потоками, CPU only → оценить смысл → на подходящем кванте проверить prompt/temperature/budget → при необходимости сравнить окна 8192/4096 отдельными запусками. Для окна 4096 заранее проверить фактическую длину prompt и резерв ответа: не запускать переполнение и не обрезать доказательства. Квантование и окно требуют перезагрузки только маленького собственного сервера, а параметры запросов — нет.

cpu_experiment.py запускает по одному своему llama-server на 127.0.0.1:8081, проверяет свободный порт, SHA-256, /health, пишет команду и отдельный лог, выполняет одинаковый прогрев, отключает prompt cache и в finally останавливает только созданный процесс. Готовые отчёты не перезаписывает. Измеряет отдельно загрузку сервера, размер весов на диске и sampled peak RSS процесса/среднюю CPU-загрузку каждые 250 мс. RSS — резидентная память процесса, не размер весов; CPU может превышать 100% на нескольких ядрах. GPU snapshots остаются общесистемными и могут показывать занятую Strata: не приписывать их CPU-модели. CPU подтверждать флагами и журналом allocations. timings API сохраняются, если сервер их возвращает.

Первый пилот: 6 вопросов × 1 повтор × 3 кванта = 18 вызовов плюс 3 прогрева. Это диагностический набор, не достаточная статистика для вывода о победителе. Финальное сравнение повторить по три раза. Нижеследующий план для большой модели сохраняется как альтернативный маршрут; новые CPU-результаты не сравнивать с исторической Strata как изолированный эффект квантования.

Нельзя сравнивать новые времена с историческими как контролируемый эксперимент.

## Ограничение: дорогая перезагрузка большой модели

Основной маршрут — **ноль перезагрузок**. Benchmark не запускает, не останавливает и не конфигурирует сервер. Temperature, max_tokens и system prompt отправляются в запросе. Когда модель освободится, один проверочный вызов и монитор сервера подтвердят поддержку параметров. Если сервер их игнорирует, фиксируем ограничение и не выдаём конфигурацию запроса за применённую настройку.

Не меняем context window занятой модели. Настоящее окно — настройка сервера; поле --context-window только записывает подтверждённое значение в отчёт. Сокращение текста запроса не меняет окно и не гарантирует уменьшение зарезервированного KV cache. Объём входного контекста исследуем отдельно, после главного сравнения: из сохранённых фрагментов исключаем только нерелевантные, перенумеровываем ссылки, сохраняем обязательные источники, сверяем качество поиска. Это эксперимент над RAG, не изолированный эффект настройки LLM.

IQ3_S уже используется. Не скачиваем веса, не запускаем вторую большую модель рядом с текущей и не меняем квантование ради формального пункта. Опциональное сравнение другого квантования — только в запланированное окно обслуживания, если есть совместимые локальные веса и ресурсы. Сначала полностью измеряем текущий вариант, затем один раз загружаем другой; сохраняем тот же набор, prompt, режим reasoning, окно, offload и параметры. Отмечаем влияние порядка, прогрева и разных запусков. Если такого сравнения нет, честно пишем: квантование используется, альтернативы не измерены.

## Этап 2. Поиск улучшения без перезагрузки

Пять профилей: baseline (0.1/4096/исходный prompt); temperature (0/4096/исходный); budget (0.1/2048/исходный); prompt (0.1/4096/уточнённый); candidate (0/2048/уточнённый). Первые четыре выделяют по одному изменению, candidate проверяет сочетание. Уточнённый prompt просит прямой ответ, максимум шесть коротких пунктов, все условия и идентификаторы, исправление ложных предпосылок, границы подтверждённых данных.

1. Начать с одного повтора baseline + prompt: 12 вызовов, ранняя проверка гипотезы о краткости без потери фактов.
2. Если шаблон полезен, проверить temperature и budget по одному повтору. Проверить RSS на truncation/пустой content и потери условий. При регрессии бюджета сохранить 4096; не продолжать слабую конфигурацию только ради меньшего времени.
3. Выбранный профиль сравнить с baseline по три повтора на шести вопросах: 36 вызовов. CLI позволяет выбрать любые профили; candidate — лишь название гипотезы, не победитель. Отчёты разных этапов сохранять под разными именами.
4. Запросы идут последовательно; порядок профилей меняется между повторами. Это уменьшает систематическое смещение, но не устраняет prompt cache. Не чистить кеш ценой перезагрузки. Записать политику кеша сервера и провести один одинаковый неоцениваемый прогрев вручную при необходимости.
5. Не добавлять неподтверждённые API-флаги thinking/context. Сохранять режим reasoning сервера одинаковым. Temperature=0 не является гарантией детерминизма.

## Этап 3. Качество и ресурсы

Каждый ответ сверить с frozen источниками. manual_quality: 0 — неверно/пусто/выдумано; 1 — частично верно, пропущено условие или источник; 2 — все запрошенные факты верны, ссылки подтверждают их, отказ/исправление предпосылки корректны. В quality_notes записать конкретные пропуски. Проверка номеров ссылок сама по себе не оценивает смысл. Для слепой оценки скрыть profile и перемешать ответы в отдельной копии.

В отчёте есть полный ответ, SHA-256, usage, finish_reason, полный HTTP latency, ошибки и медиана успешных вызовов. Не путать latency с TTFT или чистой скоростью декодирования; usage может включать reasoning. Ошибки и truncation показывать отдельно от медианы, неизвестные поля оставлять неизвестными.

nvidia-smi снимается до и после запроса: память MiB, загрузка %, мощность W, все GPU. Это снимки устройства целиком, не пик и не VRAM конкретной модели. Дополнительно для видео/таблицы замерить монитором Strata или ОС RAM процесса, VRAM и скорость decode в одинаковые периоды. Если нет инструмента — указать «не измерено». Не обещать сокращение VRAM от меньшего max_tokens: сервер может резервировать память независимо от запроса. Нулевой GPU snapshot означает недоступный замер, а не нулевую нагрузку.

Критерий выбора: отсутствие ошибок/обрезания и смысловой регрессии на каждом критическом кейсе; затем меньшая медиана времени или более краткий ответ. При шести вопросах и трёх повторах вывод относится только к этому набору. Если кандидат хуже, выбрать prompt/temperature с 4096 либо оставить baseline. Готовый benchmark ещё не является оптимизированной моделью.
