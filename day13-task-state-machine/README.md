# День 13. Состояние задачи (Task State Machine)

**Видео-демо:** [day13-demo.mp4 на Яндекс.Диске](https://yadi.sk/i/2I4MfudGIiRvNQ) — формальный автомат проходит planning → execution → validation → done, сохраняет паузы и контекст после перезапуска, а DeepSeek V4 Flash и GPT-OSS 20B через Wormsoft выполняют один и тот же шаг рядом.

Задача представлена конечным автоматом `planning → execution → validation → done`. Для каждого состояния явно заданы текущий шаг и ожидаемое действие. Переходы проверяются кодом, поэтому агент не может перескочить этап или выполнить действие во время паузы.

## Что переиспользовано из предыдущих дней

- SQLite-хранилище и безопасная работа с соединениями — развитие подхода трёх слоёв памяти дня 11.
- Разделение агента, хранилища и локального HTTP-интерфейса — архитектурный паттерн дней 11–12.
- Автоматическая запись браузерного демо через Chrome CDP и ffmpeg — инфраструктура прошлых дней.

Состояние задачи не смешано с памятью диалога или профилем пользователя. В БД сохраняются цель, этап, шаг, ожидаемое действие, пауза, версия, результаты этапов и журнал событий.

## Сравнение моделей

На любом активном этапе один и тот же неизменяемый снимок состояния можно отправить двум моделям:

- `deepseek-v4-flash` через DeepSeek;
- `openai/gpt-oss:20b` через Wormsoft.

Интерфейс показывает ответы и время рядом. Выбор ответа только переносит его в поле результата: автомат меняет этап лишь после отдельного ожидаемого действия. Для живого сравнения нужны `DEEPSEEK_API_KEY` и `WORMSOFT_API_KEY`.

## Контракт состояний

| Этап | Текущий шаг | Ожидаемое действие | Следующий этап |
|---|---|---|---|
| `planning` | Составить и согласовать план | `approve_plan` | `execution` |
| `execution` | Выполнить согласованный план | `complete_execution` | `validation` |
| `validation` | Проверить результат | `approve_validation` | `done` |
| `done` | Задача завершена | — | — |

`pause` не меняет этап, шаг и ожидаемое действие. `resume(task_id)` поднимает их вместе с исходной целью и артефактами, поэтому повторное объяснение не требуется. Оптимистическая версия защищает от одновременной записи устаревшего состояния.

## Что показано в видео

1. Создание задачи: `planning`, текущий шаг и `approve_plan`.
2. Неверный переход блокируется автоматом.
3. Пауза и продолжение на `planning`.
4. Переход в `execution`, пауза, «новый процесс» через очистку экрана и загрузку только по `task_id`; цель и план восстанавливаются без повторного ввода.
5. Переход в `validation`, ещё одна пауза и продолжение.
6. Переход в `done`, все артефакты и полный журнал событий.
